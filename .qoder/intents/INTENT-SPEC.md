# INTENT-SPEC：需求意图文档方法论（什么是好的 intent）

> **定位**: `.qoder/intents/` 资产库的**方法论权威文档**——建档质量判据与写作规范。消费方: architect Step 0.5（建档执行）、02-clarification（采访产出）、god/audit（溯源对照）、未来读者（项目理解）。
> **版本**: V1.0.0（2026-09-09，task-103 W1 推演定稿）

---

## 一、第一性定性：起点契约，不是终点规格

> intent 回答 **"为什么做、做什么算对"**；spec/plan 回答 **"怎么做"**。

- intent 是制品链（intent → spec → plan → sandbox → coding/testing → audit）的**起点契约**——可审查、可版本化、机器可校验的入参；
- 意图层**禁止写技术方案**（表/API/组件/库选型）：写了 = 意图泄漏实现，锁死 architect 设计空间、污染资产库；
- 技术细节留给 spec/plan 层，每层只加自己的信息，**不回写意图**（防污染）。

## 二、消费者矩阵（结构由消费者决定）

| 消费者 | 需要什么 | 决定的结构 |
|--------|---------|-----------|
| architect（入参） | 做什么/不做什么/怎么做算对/域线索 | 目标 + 边界 + 可验收期望 |
| 发起者（确认对齐） | 自己的语言可读 | 发起者语言、五分钟可复述 |
| god/audit（执行对照） | 可判定的行为基准 | 防 scope creep 核对锚点 |
| 资产库/未来的人（理解项目） | 域归属/来源/演进 | frontmatter 结构化 + 版本化 |
| 机器（validate） | 结构化字段 | frontmatter 契约（title/domain/status/…） |

## 三、好的 intent 五判据（QUALITY）

| 判据 | 定义 | 自检问句 | 可机器化 |
|------|------|---------|---------|
| **A 原子性** | 一个 intent = 一个"痛点→期望"对 | 能拆成两个独立对吗？ | 部分（人工） |
| **B 行为性** | 期望结果写行为/结果改变，不写方案 | 删掉实现词（表/API/组件）后语义完整吗？ | 关键词警示 |
| **C 边界显式** | 排除项 ≥1 | 无事可排 = 边界未想清？ | 排除项为空 → 警示 |
| **D 可验收** | 期望结果可观察可判定 | audit 能对照"做的是不是当初要的"吗？ | 人工核对 |
| **E 五分钟可读** | 一段话能复述 | 能讲给同事听且不失真吗？ | 长度上限 |

## 四、结构规范与写作指南

### frontmatter（机器契约，字段最小集）

```yaml
title:   需求一句话标题（发起者语言，非技术术语）
domain:  对齐 domain-index.json 的 domain 域名称；未建档域 → 域缺口登记（注记放正文）
status:  draft | confirmed | archived
created / updated: YYYY-MM-DD
plan:    产出 plan 后回填（task-XXX）；未立项 null
```

### 正文 5 要素（人机共读，按序书写）

| 要素 | 回答 | 好写法 | 坏写法 |
|------|------|--------|--------|
| **痛点** | 谁在什么场景遇到什么阻碍？ | 具体 actor + 场景 + 后果（含一次真实例子最佳） | "系统不好用""体验差" |
| **期望结果** | 完成后什么行为/结果会改变？ | 可观察的行为/结果句（"HR 能在 X 步内完成 Y"） | "增加一个 XX 页面""接 XX 接口" |
| **影响范围** | 涉及哪些用户/系统/数据？ | 三面点名，未知显式写"待确认" | 省略（= 未想清） |
| **约束与排除项** | 哪些规则必须遵守？哪些本次不做？ | 政策/技术约束 + **至少 1 条排除项** | "无限制"（罕见，须声明理由） |
| **未决问题** | 哪些判断需要负责人回答？ | 每条带倾向与理由（"倾向 X，因…"） | 只问不答（把决策全抛给人） |

### 可选：补充上下文（context）

发起者语言记录背景/来源/领域知识——帮助 architect 快速定位；**禁止技术方案与实现细节**。

## 五、反例集（什么不是好的 intent）

1. **方案混入**: 期望结果写"增加 leave_application 表 + /api/query 接口" → 意图泄漏实现（违 B）；
2. **痛点无 actor**: "数据同步有问题" → 谁？什么场景？（违 A/B）；
3. **范围省略**: 只写目标不写影响面 → 下游无法评估爆炸半径（违 C）；
4. **无排除项**: 什么都不排 → 边界未想清，必然 scope creep（违 C）；
5. **未决无倾向**: "用 A 还是 B？" 不带推荐 → 把架构决策推回给发起者（违 E）。

## 六、与下游的关系（每层只加自己的信息）

```
intent（起点契约：为什么/做什么算对）
  → architect Step 0.5 建档确认
  → architect 需求基线（域引用/复用决策/风格/表清单）   ← spec 侧
  → plan 详情 + 评分卡 + 校验矩阵                        ← plan 侧
  → god 执行对照 / audit 核对"实现 vs intent"            ← 消费侧
```

- intent 变更（范围/目标调整）→ 更新 intent 文档（版本化）→ 关联 plan 标注 revised；
- 下游产物（基线/plan/代码）**不回写** intent——保持意图纯净。

## 七、skill 化裁决（2026-09-09，task-103 决策点 D6）

**结论：不新建独立 skill**（如 intent-capture），采用"规范文档化 + 协议内嵌 + 消费端引用"三件套：

| 维度 | 分析 |
|------|------|
| 触发时机 | 与 architect 完全重叠（收到新需求）——独立 skill = 路由歧义（02 以 rule 非 skill 存在的同因） |
| 产物协议 | intent 文档是跨阶段共享资产（architect/god/audit/资产库）——位置 = 本目录，非某 skill 内部 |
| 执行者能力 | 采访已在（grill-me/02-clarification）——不重复造 |
| 沉淀载体 | 本文件（方法论）+ intents/README（使用规范）+ _TEMPLATE（模板）——资产自治，消费端引用 |

**skill 化边界条件**（触发后重议）: 出现"非 AI 会话的直接需求入口"（产品经理手动建档 / TAPD 工单批量导入 / 外部系统需求投递）——建档成为独立高频流程时，才值得独立 skill。
