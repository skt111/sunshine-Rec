# 供给端雷达：高校招聘活动自动采集与统一查看

> 本文档为**需求意图（intent）结构化档案**——architect 规划入参，非实现规格。
> 使用规范见本目录 README.md；写作判据见 INTENT-SPEC.md。
> **需求侧基线**: `.qoder/docx/供给端雷达-需求包/` **v1.0**（自检报告 REQ-STATS verdict=pass）

## 意图（5 要素）

- **痛点**:
  HR / 招聘团队需要持续掌握各高校的宣讲会、双选会、招聘会安排，但目前只能**人工逐校浏览** 54 所高校就业信息网、手工记录到表格。由此产生四类实际阻碍：
  1. **信息滞后**——活动临时发布，人工巡检跟不上，常错过报名截止或参会时间；
  2. **覆盖不全**——人力有限只能盯少数目标校，大量高校活动未被发现；
  3. **无法横向对比**——校内/校外、城市、活动类型散落在不同网站，难以一屏对比近期安排；
  4. **变更不可追溯**——活动改期/取消后，原记录失效且无历史痕迹。

- **期望结果**:
  HR 登录现有系统后，在「供给端雷达」页签内**一屏完成**以下动作（均基于真实采集入库数据）：
  1. 看到大盘指标（监测高校数、活动总数、近期宣讲会数、近期双选会数、待核验数）；
  2. 按高校（搜索/多选/城市）、活动分类、时间范围、活动状态、举办形式、核验状态**组合筛选**；
  3. 在「全部 / 校内宣讲会 / 校外宣讲会 / 校内双选会 / 校外双选会 / 其他就业活动」间切换，各页签数量真实；
  4. 点开任一活动查看完整详情（时间/地点/主办/企业/报名/原始说明/来源链接/最近采集/核验状态/最近变更）；
  5. 按**高校分组**查看各校近期动态与采集健康度；
  6. 触发一次采集并看到**真实进度与终态**（未完成不得显示成功）。
  无数据时展示明确空态，**不得用模拟数据冒充真实结果**。

- **影响范围**:
  - **用户**：系统内部 HR / 招聘团队；单一角色，权限一致（不区分管理员/查看者）。
  - **系统**：现有前端（Vue 2.6 + iView）新增页面与顶部导航页签；现有后端（Spring Boot）新增采集与查询能力；MySQL `sunshine` 库新增四类数据（高校站点配置 / 活动 / 采集任务 / 活动变更记录）。
  - **数据**：54 所高校就业信息网**公开页面**（只读采集）；不读写现有业务表；不改动其他模块。

- **约束与排除项**:
  - **必须遵守**：
    1. 采集必须 Java 实现，**禁用 Python**；
    2. 数据必须入库，**禁止以 Excel 导出作为交付**；
    3. 遇登录墙 / 验证码 / 访问限制必须**停止并记录**，不得绕过；
    4. **不得**依据高校所在地推断活动一定在校内举行；
    5. 单校采集失败**不得中断**整体任务；
    6. 请求失败**不得删除**原有数据；
    7. 不得编造高校网址（以随包清单为唯一来源）。
  - **本次不做（排除项）**：不做活动内容 AI 摘要；不做变更消息/邮件推送；不做趋势图表（按月统计活动量）；不做核验状态的写入（仅只读展示）；不做移动端适配；不改动现有其他业务模块。

- **未决问题（均带倾向）**:
  1. **前端菜单注册方式**——✅ **已确认（2026-10-26）**：采用**后端菜单数据驱动**（沿用现有 `menuList` 机制，在后台配置菜单项 `sysMenuCode`/`menuUrl`，与权限体系统一）。
  2. **Playwright 浏览器内核安装**——✅ **已确认（2026-10-26）**：采用方案 A，部署环境安装 Chromium（JS 渲染站点走 Playwright，静态站点优先 Jsoup）；内核不可用时降级纯 Jsoup 并登记。
  3. **首批试采范围**——✅ **已确认（2026-10-26）**：先跑清单推荐的 **9 所**验证闭环，通过后再扩至 54 所。
