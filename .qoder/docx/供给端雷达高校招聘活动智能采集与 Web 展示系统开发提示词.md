# 供给端雷达——高校招聘活动智能采集与 Web 展示系统开发提示词

## 一、项目目标

请在现有「阳光校招情报与人才战略决策系统」中，开发顶部页签「供给端雷达」对应的完整页面及后端数据采集功能。

本模块用于自动采集各高校就业信息网公开发布的宣讲会、双选会、招聘会及其他就业活动，并将采集结果直接展示在 Web 页面中，替代原有人工浏览高校网站、手动记录招聘活动的工作方式。

**核心要求：使用 Java 编写爬虫，使用数据库保存数据，通过后端 API 向 Web 前端提供数据。禁止将 Excel 导出作为本模块的数据交付方式。**

整个业务流程：

高校网站发现 → 招聘活动采集 → 活动详情解析 → 类型识别 → 数据去重与更新 → 数据库存储 → 供给端雷达展示 → 按学校筛选和查看。

## 二、现有系统集成要求

### 2.1 集成现有主页面

不要单独创建一个与现有系统无关的网站，也不要重建已有的主页面。

请先检查当前项目目录、前端路由、顶部导航、页面组件及后端 API 结构，在现有工程基础上开发。

在主页面顶部导航栏中，将「供给端雷达」作为一个独立页签。

点击该页签后，进入高校招聘活动情报页面。

如果现有导航中已经存在该页签，则直接接入对应页面，不得重复添加。

保留现有系统的品牌配色和整体视觉规范：

- 主色：橙色 `#F58220`。
- 页面背景：暖白色或浅灰色。
- 内容卡片：白色背景。
- 重要数据：橙色强调。
- 文字：深灰色。
- 整体采用现代企业级 SaaS 数据平台风格。

页面需要具备清晰的信息层次、合理的数据密度和良好的桌面端展示效果。

## 三、Java 后端采集架构

采用 Java 实现高校招聘活动采集功能，不使用 Python。

优先沿用现有后端框架。如果当前项目采用 Spring Boot，则继续使用 Spring Boot；如果已经有数据库、ORM 和任务调度组件，则优先复用。

推荐技术：

- Java 17 或现有项目兼容版本。
- Spring Boot。
- Jsoup：解析普通 HTML 页面。
- Java HttpClient 或 OkHttp：发送 HTTP 请求。
- Playwright for Java：处理需要 JavaScript 渲染的公开页面。
- Jackson：解析 JSON。
- MyBatis-Plus：数据库操作，若现有项目使用该技术。
- MySQL 或现有项目数据库。
- Spring Scheduler 或 Quartz：定时采集任务。

### 3.1 高校网站配置

读取已有文件《主要高校就业招聘网站清单_修正版.md》，将高校名称、城市、网址和备注整理为可维护的站点配置。

如果文件不在当前项目目录，先查找已有配置或向用户确认文件位置，不得自行编造高校网址。

每所高校至少记录：

- 高校 ID。
- 高校名称。
- 所在城市。
- 就业网站入口。
- 站点适配器类型。
- 是否启用采集。
- 最近采集时间。
- 最近采集状态。
- 最近失败原因。

不同高校的栏目名称和网页结构不统一，必须支持通用解析器与高校专用适配器。

### 3.2 活动入口发现

不能只抓取标题包含“宣讲会”或“双选会”的页面。

还需要检查：

- 就业活动。
- 招聘活动。
- 就业信息。
- 招聘信息。
- 校园招聘。
- 校园宣讲会。
- 招聘会、双选会。
- 通知公告。
- 招聘日历、就业日历。
- 企业进校活动。
- 其他与毕业生就业直接相关的公开栏目。

先发现候选活动，再进入详情页判断活动性质。

如果某所学校把宣讲会和双选会统一放在“就业活动”栏目中，也必须能够发现和采集。

对需要 JavaScript 才能展示的公开页面，使用 Playwright for Java；普通 HTML 页面优先使用 Jsoup。

遇到登录、验证码、访问限制或明确的访问控制时，应停止自动尝试并记录异常，不得绕过访问控制。

## 四、招聘活动分类规则

系统必须覆盖以下四类核心活动：

1. 校内宣讲会。
2. 校外宣讲会。
3. 校内双选会。
4. 校外双选会。

同时保留其他就业相关活动，不得强行将所有记录归入四类。

建议分别维护三个字段：

- `eventType`：活动本身的类型。
- `venueType`：活动举办地点属性。
- `standardCategory`：前端展示使用的标准分类。

### 4.1 活动类型

建议包含：

- `TALK`：宣讲会。
- `JOB_FAIR`：双选会或招聘会。
- `RECRUITMENT_EVENT`：其他招聘活动。
- `EMPLOYMENT_SERVICE`：就业服务活动。
- `OTHER_EMPLOYMENT_ACTIVITY`：其他就业相关活动。
- `UNKNOWN`：待判断。

### 4.2 举办地点属性

建议包含：

- `ON_CAMPUS`：校内。
- `OFF_CAMPUS`：校外。
- `ONLINE`：线上。
- `HYBRID`：线上线下混合。
- `UNKNOWN`：未知。

### 4.3 标准分类

- `ON_CAMPUS_TALK`：校内宣讲会。
- `OFF_CAMPUS_TALK`：校外宣讲会。
- `ON_CAMPUS_FAIR`：校内双选会。
- `OFF_CAMPUS_FAIR`：校外双选会。
- `OTHER`：其他就业活动。
- `PENDING_REVIEW`：待人工核验。

分类时优先采用学校原始活动类型、详情页描述和明确的举办地点。

如果只知道活动属于宣讲会，但无法判断举办地点，应保留宣讲会类型，将地点标记为未知，并进入复核流程。

不能根据发布活动的高校所在地直接推断活动一定在校内举行。

## 五、数据库设计

所有采集结果直接保存到数据库，不以 Excel 文件作为中间交付物。

建议建立以下数据表：

### 5.1 高校站点表 `university_site`

保存高校名称、城市、网站入口、适配器类型、启用状态和采集状态。

### 5.2 招聘活动表 `employment_event`

至少包含：

- `id`：内部活动 ID。
- `schoolId`：发布活动的高校 ID。
- `schoolName`：高校名称。
- `schoolCity`：高校所在地。
- `eventTitle`：活动名称。
- `eventType`：标准活动类型。
- `eventTypeOriginal`：学校原始活动类型。
- `venueType`：校内、校外、线上等属性。
- `standardCategory`：前端标准分类。
- `eventDate`：活动日期。
- `startTime`：开始时间。
- `endTime`：结束时间。
- `venueName`：举办场馆。
- `eventAddress`：详细地点。
- `organizer`：主办单位。
- `companyNames`：相关企业名称，如有。
- `registrationDeadline`：报名截止时间，如有。
- `registrationUrl`：报名链接，如有。
- `eventDescription`：活动说明。
- `sourceListUrl`：来源列表页。
- `sourceUrl`：来源详情页。
- `sourcePublishedAt`：来源发布时间。
- `crawledAt`：采集时间。
- `lastSeenAt`：最近一次发现该活动的时间。
- `eventStatus`：活动状态。
- `verificationStatus`：数据核验状态。

### 5.3 采集任务表 `crawl_task`

记录高校采集任务、开始时间、结束时间、成功数量、失败数量及异常原因。

### 5.4 活动变更记录表 `employment_event_history`

记录活动时间、地点、名称、取消状态等关键字段的变更，避免覆盖后无法追溯。

### 5.5 去重与更新

优先使用网站提供的稳定活动 ID。

没有稳定 ID 时，结合高校、原始详情链接、活动标题、日期和地点进行去重。

重复采集时更新已有记录，而不是无限新增。

对于时间变化、地点变化、延期或取消的活动，更新活动状态并保留变更记录。

请求失败不得直接删除原有数据。

## 六、供给端雷达 Web 页面设计

这是本次开发的核心交付内容。

页面通过后端 API 读取数据库中的招聘活动，直接展示在现有系统的「供给端雷达」页签中。

不要生成静态截图来代替真实页面，也不要只展示模拟数据。

### 6.1 页面顶部：标题与采集状态

页面标题：

**供给端雷达**

副标题：

「高校招聘活动实时追踪 · 宣讲会 · 双选会 · 就业活动」

右上方显示：

- 最近一次采集时间。
- 当前纳入监测的高校数量。
- 最近一次采集状态。
- 「立即更新」按钮。
- 「采集任务」入口。

点击「立即更新」后，调用后端采集任务 API，并展示任务执行状态。

任务执行期间显示运行中状态；任务结束后刷新相关数据。不得在采集尚未完成时提前显示成功。

### 6.2 第一层：核心统计卡片

在页面顶部展示以下统计指标：

1. 监测高校数。
2. 累计活动数。
3. 近期宣讲会数量。
4. 近期双选会数量。
5. 待核验活动数量。

统计数据必须来自数据库查询结果。

可以根据当前筛选条件动态更新统计值，但需要明确统计口径和时间范围。

如果当前没有真实数据，应展示空状态，而不是伪造真实统计数字。

### 6.3 第二层：高校筛选区

这是页面最重要的交互之一。

提供以下筛选条件：

**高校筛选**

- 支持高校名称搜索。
- 支持从高校下拉列表选择。
- 支持选择多个高校。
- 支持按高校所在城市筛选。
- 支持「全部高校」选项。

**活动筛选**

- 全部活动。
- 校内宣讲会。
- 校外宣讲会。
- 校内双选会。
- 校外双选会。
- 其他就业活动。
- 待人工核验。

**时间筛选**

- 今日。
- 未来 7 天。
- 未来 30 天。
- 自定义日期范围。

**其他筛选**

- 活动状态。
- 线上、线下或混合形式。
- 数据核验状态。

支持组合筛选。

例如，用户可以选择「北京地区 + 北京大学 + 校内宣讲会 + 未来 30 天」，只展示符合条件的活动。

提供「重置筛选」按钮。

筛选条件变化后，通过后端 API 获取符合条件的数据，并同步更新统计卡片、活动列表和分页信息。

### 6.4 第三层：活动分类页签

在筛选区下方设置活动分类页签：

- 全部活动。
- 校内宣讲会。
- 校外宣讲会。
- 校内双选会。
- 校外双选会。
- 其他活动。

每个页签可以显示对应活动数量。

数量必须从数据库实时统计，不能写死。

点击页签后，列表切换至对应分类。

「全部活动」用于综合查看各高校招聘动态。

### 6.5 第四层：活动展示列表

采用清晰、专业的招聘活动列表卡片布局。

每条活动至少展示：

- 活动日期。
- 活动名称。
- 发布高校。
- 高校所在城市。
- 活动分类标签。
- 开始时间和结束时间。
- 举办地点。
- 线上或线下属性。
- 活动状态。
- 数据来源。
- 最近采集时间。

活动卡片示例：

**北京大学 2027 届校园招聘宣讲会**

- 分类：校内宣讲会
- 时间：2026-10-27 14:00—16:00
- 地点：校内某教学楼（以来源页面为准）
- 来源：北京大学就业信息网
- 状态：未开始

以上仅用于说明展示结构，不代表真实活动数据。

卡片中应提供：

- 「查看详情」。
- 「打开原始来源」。
- 「标记待核验」或相应的数据核验入口。

不要将未确认的信息伪装成真实场地、时间或招聘状态。

### 6.6 第五层：活动详情抽屉

点击活动卡片后，在右侧打开详情抽屉，不需要跳转离开当前列表。

详情应包含：

1. 活动基本信息。
2. 活动类型与地点分类。
3. 日期和时间。
4. 举办地点。
5. 主办单位及相关企业。
6. 报名截止时间和报名方式。
7. 原始活动说明。
8. 来源高校及原始详情链接。
9. 最近采集时间。
10. 数据核验状态。
11. 最近一次内容变更记录。

对于缺失字段，显示「暂无公开信息」，不要展示虚构值。

点击「打开原始来源」时，在新浏览器标签页打开原始网页。

### 6.7 第六层：按学校分组查看

除了普通列表，增加一种按高校分组的查看模式。

提供两种视图切换：

- **活动列表视图**：按照活动日期排序，便于查看近期招聘安排。
- **高校分组视图**：按高校分组展示活动，每所高校显示活动数量及近期活动。

高校分组卡片包含：

- 高校名称。
- 所在城市。
- 当前筛选条件下的活动数量。
- 最近采集时间。
- 最近采集状态。
- 近期活动摘要。
- 展开或收起活动列表的操作。

点击某所高校后，可以只查看该高校的全部招聘活动，并进一步按四类活动筛选。

分组模式必须使用数据库中的高校 ID 进行关联，避免仅靠学校名称模糊匹配造成数据混淆。

### 6.8 第七层：分页与排序

活动列表支持：

- 按活动日期升序。
- 按最近采集时间排序。
- 按发布时间排序。
- 分页查询。
- 调整每页展示数量。

建议默认按照活动日期升序展示近期活动。

已经结束的活动仍保留在数据库中，可以通过时间筛选查看历史信息。

分页应由后端处理，不能一次性加载全部高校的所有活动。

### 6.9 页面状态

页面必须正确处理：

- 首次加载。
- 加载中。
- 查询成功。
- 无符合条件的数据。
- 单所高校采集失败。
- 全部采集任务异常。
- 部分字段缺失。
- 活动待核验。
- 网络请求失败。

无数据时展示明确的空状态，例如：

「当前筛选条件下暂无招聘活动，请调整时间范围或高校筛选条件。」

不要用静态演示数据掩盖真实数据缺失。

## 七、前后端 API 设计

前端通过后端 REST API 访问数据。

接口路径应遵循现有项目规范；以下为建议设计。

### 7.1 获取高校列表

`GET /api/supply-radar/schools`

支持按城市、关键词和是否启用采集筛选。

返回高校 ID、名称、城市及采集状态。

### 7.2 获取活动列表

`GET /api/supply-radar/events`

建议支持：

- `schoolIds`：高校 ID 列表。
- `city`：城市。
- `category`：标准活动分类。
- `eventType`：活动类型。
- `venueType`：地点属性。
- `startDate`：开始日期。
- `endDate`：结束日期。
- `status`：活动状态。
- `verificationStatus`：核验状态。
- `keyword`：标题或正文关键词。
- `page`：页码。
- `size`：每页条数。
- `sortBy`：排序字段。
- `sortDirection`：排序方向。

返回分页数据，包括：

- 活动记录。
- 总记录数。
- 当前页码。
- 每页条数。
- 总页数。

所有查询条件必须使用后端安全校验，防止无效参数和 SQL 注入。

### 7.3 获取统计指标

`GET /api/supply-radar/statistics`

返回高校数量、活动总数、四类活动数量、其他活动数量、待核验数量等统计数据。

支持与活动列表相同的主要筛选条件，确保统计数据与当前视图保持一致。

### 7.4 获取活动详情

`GET /api/supply-radar/events/{id}`

返回完整活动信息、来源链接和变更记录。

### 7.5 启动采集任务

`POST /api/supply-radar/crawl-tasks`

支持：

- 采集全部已启用高校。
- 采集指定高校。
- 采集指定时间范围内的新增或更新信息。

任务提交后返回任务 ID 和初始状态。

### 7.6 查询采集任务

`GET /api/supply-radar/crawl-tasks/{taskId}`

返回任务状态、开始时间、结束时间、处理数量、成功数量、失败数量和错误摘要。

前端通过轮询或现有系统的消息机制获取进度。

### 7.7 查询采集状态

`GET /api/supply-radar/crawl-status`

返回每所高校最近一次采集时间、成功状态和错误原因。

所有接口均应返回统一的 JSON 结构，并遵循现有项目的身份认证、权限控制和错误处理规范。

## 八、前端技术实现要求

优先使用现有前端项目的框架、组件库、路由和请求封装。

如果现有项目使用 Vue 3、TypeScript、Element Plus，则继续使用这些技术，不要重复搭建工程。

建议将页面拆分为：

- `SupplyRadarPage`：供给端雷达主页面。
- `RadarStatistics`：顶部统计卡片。
- `SchoolFilter`：高校筛选组件。
- `EventCategoryTabs`：活动分类页签。
- `EventList`：活动列表。
- `EventCard`：单条活动卡片。
- `EventDetailDrawer`：活动详情抽屉。
- `SchoolGroupedView`：高校分组视图。
- `CrawlTaskPanel`：采集任务及进度。
- `CrawlStatusTable`：高校采集状态。

筛选条件、分页、活动详情及采集任务状态必须有真实交互。

不要仅制作静态 UI，也不要把模拟数据混入正式数据库。

## 九、开发与验收顺序

### 第一步：检查现有项目

确认前端框架、顶部导航实现、后端技术栈、数据库结构及已有高校清单。

### 第二步：完成 Java 采集框架

先支持高校配置、栏目发现、详情解析、分类、去重和数据库持久化。

优先选取至少 5 所不同结构的高校进行真实试采集。

### 第三步：开发后端 API

实现高校列表、活动列表、统计指标、活动详情、采集任务和采集状态接口。

### 第四步：开发供给端雷达页面

将页面接入主页面顶部导航，完成高校筛选、四类活动切换、其他活动查看、活动列表、详情抽屉和高校分组视图。

### 第五步：端到端验证
