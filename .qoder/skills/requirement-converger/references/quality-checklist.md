# S3 质量自检 · 清单与报告模板（需求文档收束器）

> 用途: S3 阶段逐项自检——C1-C8 判据 + 自检报告模板。
> 原则: **任一项不通过 → 修订后重检 → 禁止带缺口交付**；每项自检必须留证据（对数结果/搜索记录/试写产物），写入自检报告。
> V1.1.0: 新增 REQ-STATS 结构行（机器可断言——报告尾部一行，verdict 自洽 + 多轮更新原行）。
> V1.2.0: 新增「原则 ↔ 检查项映射」§0（两套 7 条对齐，免脑内映射）。
> V1.3.0: 新增 C8「数据契约完备性」（L1 必做 + 逐层判定；整项 na 仅限无数据面/旧包——唯一定义见 §C8，防逃检）。
> V1.4.0: REQ-STATS 扩容 counts（pages/tables/endpoints——与 C1 对数同源）；报告模板增「独立核验 / 消费回执」小节；使用纪律增两条（独立核验触发强制 / 回执回填）；C1 增采访覆盖对账（九类三向对数）。

## 0. 原则 ↔ 检查项映射（核心原则 7 条 × C1-C8）

| 核心原则（7 条） | 对应检查项 | 说明 |
|------------------|-----------|------|
| 显式 | C3 无歧义性 | 模糊词转译即"显式"的检验动作 |
| 可枚举 | C1 可枚举性 | 数量对数 |
| 可验证 | C2 可验证性 | 级别×证据矩阵 |
| 关注点分离 | C4 关注点分离 | 分册单源 |
| 留白显式 | C5 留白显式 | 三分法登记 |
| 单源化 | C6 版本单源化 | 版本/引用纪律 |
| 有据可查 | C7（兼顾） | 试写溯源 + 参考节蓝本锚定——"有据"由"可溯源"检验 |
| 显式 + 可验证（数据域深化） | **C8 数据契约完备性** | 字段级必做 + 关系/口径写死（显式）+ 历史表核对脚本化（可验证） |

> 注：C7 为端到端消费检验（任务书可生成性），同时承担"有据可查"红线与"入参 API 可用性"双重检验；C8 为数据域横向深化，不引入新原则。

## C1 可枚举性

**判据**（数量对数——三处一致）:

| 清单 | 应对数的三处 |
|------|-------------|
| 页面数 | README 速览计数 = §一 建设范围表行数 = §八 验收清单行数 |
| 表清单 | §五 表清单（按域计数）= 附录A 表定义（按域计数） |
| 端点数 | §六/README 计数 = 附录B 端点小节数 |
| 角色/交付物/红线 | 各处清单无"若干/等等/类似" |

- **采访覆盖对账（V1.4.0）**: I1-I9 九类采访 → 需求要素表 → 留白登记表**三向对数**——每类须有答复落表或留白登记（两者皆无 = 漏类；粒度=**类级**——子问级遗漏由采访指南子问清单人工保障，接受该边界）；

**通过标准**: 全部对数为等，且无模糊量词；九类采访方向全覆盖（答复或留白，二者必有其一）。
**反例**: "等 13 个页面"（数量词与列表不符）；README 写 5 域而正文 6 域。

## C2 可验证性

**判据**:
- §十一 验证手段矩阵**覆盖 §八 全部验收项**（逐行可对照，允许合并行但不得缺行——合并行须标注覆盖编号/页码）；
- 每验收项有: 验证级别（L0-L3） + 证据形式（构建日志/截图/接口响应/录屏…）；
- 验收点本身可判定（"保存成功"可判定；"体验流畅"不可）；
- 🚨 有可运行环境时声明"验收面不得低于 L2"；缺环境的级别有挂起/登记处置。

**反例**: 验收点写"界面友好"；矩阵只覆盖构建项，联调项缺行。

## C3 无歧义性（契约显式）

**判据**（核心歧义面逐面清查）:
- **响应壳**: 全文仅一套（如 `{code,message,data}`），且外部壳差异有"转发需转换、禁止混用"声明；
- **错误口径**: 业务错误 HTTP 状态（如恒 200）+ 401/403/400 映射表写死；
- **命名口径**: 声明（如前后端 snake_case / 前端内部 camelCase）；
- **枚举/状态机**: 无"等/其他"兜底词——全枚举；状态流转与终态写死；
- **模糊词清查**: 全文搜索 `适当|尽量|友好|尽快|合理|差不多|酌情`——每个出现处必须已转译为可判定行为；
- 同一事实跨册表述一致（如分页结构两套的区分声明）。

**反例**: "超时约 15 秒左右"（约+左右冗余但可接受——"尽快返回"不可）；两处响应结构互相矛盾。

## C4 关注点分离

**判据**:
- 分册职责表在案（README/主文档/附录A/B/C 各司其职）；
- 每事实一处权威: 状态机只在主文档；字段定义只在附录A；契约级关系/口径只在附录A L2/L3（附录C 简图仅为背景速览）；不复述（附录C 结尾有"以主文档与附录A/B 为准"类声明）；
- 无跨册大段复制（引用代替抄写）；改一处不需多想"还有哪里要同步"。

**反例**: 同一错误码表在主文档与附录B 各写一份且值不同。

## C5 留白显式

**判据**:
- 留白登记表存在，且每项标注三分法状态（可自行设计 / 必须对齐 / 待确认）+ 影响面 + 处理方式；
- 文档正文中凡"由开发方自行设计"处有显式声明（如"接口路径与参数结构由开发方按需求自行设计"）；
- "必须对齐"项有获取途径或就绪标准（缺的写 §十 就绪标准，不写具体值）；
- **无暗留白**: 正文中出现"待定/TBD/后续补充"但不在登记表 → 不算通过（门禁条款用语如"无 TODO 占位符"除外——须在报告中说明）。

**反例**: 密钥位置写"TODO"散落正文；接口设计授权只在聊天里说过、文档未声明。

## C6 版本单源化

**判据**:
- 文档头: 版本号 + 生成日期 + 配套材料清单；
- 变更记录节存在（首版可为"v1.0 初始版"单行）；
- README 声明下游引用方式（引用本包时携带版本）;
- 引用外部材料（如附录A 来源 DDL）标注来源与版本。

**反例**: 任务书引用"§2.2 第 8 条"而文档无此条（长任务实验实证教训）。

## C7 任务书可生成性（端到端消费检验 · 第一性）

> 需求文档=规划入参 API——入参 API 必须"可用": 下游能仅凭本包写出长任务任务书（长任务实验首启提示词样式），无需凭空补事实。

**方法**（试写检验）:
1. 依据本包**试写**任务书的: 硬约束段 + 验证面声明 + 必要挂起清单（三个片段即可）；
2. 逐句在包内**溯源**（标注节号）: 禁 DDL→§二/负面清单；外部系统边界→§六+附录B；接口设计授权→留白登记；运行配置供给→§九；验证面→§十一；挂起条件→§十；
3. 出现无法溯源（需凭空编写）的句子 = 缺口 → 回补对应节后重检。

**反例**: 任务书写了"配置从 Nacos 读取（地址 X/命名空间 Y）"但 §九 无坐标结构；任务书"验证面=构建+静态"但 §十一 要求 L2——两者矛盾未处置。

## C8 数据契约完备性（V1.3.0——逐层判定；整项 na 的唯一定义见本节末尾）

> 完备标准 = 实现侧（god）写 SQL 所需信息的全覆盖。触发分级见 templates.md §4.1。

**判据**:
- 【**L1 必做**（无论是否触发后续层）】字段级在案：每表含 字段名/类型/约束·默认值/说明/索引/唯一键；**附录A 表节数 = §五 表清单行数**（枚举字段取值列举齐全）；
- 【L2 触发——查询表链涉及 ≥2 张表的关联（联查补全 / 跨表聚合或派生 / 历史表参与的关联）】关系层在案：关联关系清单齐备（左表.列 = 右表.列 / 基数 / 连接语义 / 用途 / 物理注记——**单库=索引现状（可填"无"）；多库=跨源·应用层关联必填**）；
- 【L3 触发——**口径敏感**】口径层在案：**聚合（计数/汇总/完成度）/ 派生状态（逾期/沉默/负载）/ 联查补全（投影需跨表拼接）** 三类查询有口径契约（表链 + 过滤/聚合口径 + 参考 SQL + "等价性以口径为准"声明）；
  - **判定正例**: 带教负载=按 pairing ACTIVE 计数（L3）；完成度=DONE 数/总数（L3）；列表投影跨表拼 domain_name（L3）；
  - **判定反例**: 单表按条件查询 / 单表分页 / 单表排序 —— **不进 L3**（不判缺）；
- 【历史表触发】专项在案：使用面 DDL 摘录（最小集——非全量）+ 物理属性清单（collation / 字符集 / 时区）+ **可执行核对脚本**（只读）+ 演进/兼容注记；
  - **"可执行"基准**: 语句可在只读连接**直接运行且返回待断言列**（非"见 DBA"类占位——SQL 骨架见 templates.md §4.2）；
- 【一致性】附录A 各层表/列名与 §五 表清单一致（对数不漂移）；
- **通过标准**: L1 必做层 + 触发的层全部在案，且口径写死（语义层）、执行形态未被锁死（物理层）。
- **反例**: 附录A 仅表名节而无字段级内容（C8 仍过 = 逃检）；联查链路只存在于附录C 简图（背景参考无契约力）；口径散落正文规则行无独立契约；历史表只写"待 DBA 提供"而无使用面最小集与核对脚本；跨族 collation / 时区语义未标注；把优化级执行计划写死为唯一实现；判 na 未写依据与复检触发条件（→ 不通过）；核对脚本照抄模板骨架未填 schema/表/列实值（不可直接运行 → 不过）。

**na 唯一定义（防逃检 · 唯一权威——其余表述引用本节）**:
- `na` 仅两类适用：① 需求**不含任何表/关联/查询**（无数据面）；② **生成代际 < V1.3.0 的旧包**（以样板/报告头的"代际声明"为证）；**V1.3.0 起新包 REQ-STATS 必含 C8 字段——缺字段 = 自检不合格（不得按旧包 na）**；
- **含数据表即必检**（pass/fail）；判 na 须在报告 C8 行**写明依据与复检触发条件**；
- "未触发的层不判缺"——**逐层判定**（层未触发 ≠ 整项 na；L1 永远在判定范围内）。

## REQ-STATS 结构行（机器可断言——强制 · V1.1.0 起）

- **位置与形态**: 自检报告**末尾**一行（模板末行所示）；随包交付；
- **counts（V1.4.0 起新包必含）**: `pages/tables/endpoints`——与 C1 对数同源（下游零成本复核；历史样板可为补同步态）；
- **verdict 自洽（强制）**: C1-C8 全 pass（含 na）→ `pass`；有不通过但已登记处置（⚠️ 有条件）→ `conditional`；存在未处置不通过项 → `fail`（**禁止带 fail 交付**）；
- **C8 与 na（V1.3.0）**: 判定规则以 **§C8「na 唯一定义」为唯一权威**（含数据表即必检；na 仅限无数据面/V1.3.0 前旧包）；历史包（生成代际 < V1.3.0 且结构行无 C8 字段）按 na 处理（向后兼容）；
- **多轮规范**: 变更复检后**更新原行**（全文件至多一条，禁止追加第二条）——与版本递增同步；
- **blanks**: 留白登记表终稿条数（三分法合计）；
- **消费方**: 任务书/architect 入参核对（§0.5 gate 已接线）/audit/校验脚本按行解析（对齐 sandbox REPORT-STATS 范式）——需求包可被零成本断言。

## 使用纪律

1. **先自检后交付**: 报告随包一同输出；⏭ 无法自检的项（如需真实环境）说明原因并登记；
2. **证据可复现**: 对数/搜索/试写结果写进报告（"已检查"不算证据）;
3. **不通过处置闭环**: 修订后重检对应项，报告修订记录留痕；
4. **REQ-STATS 强制**: 报告缺 REQ-STATS 行视为自检未完成（不可交付）；变更复检后更新原行（至多一条）；
5. **独立核验（V1.4.0）**: 触达条件（≥2 域 或 ≥2 外部端点，或下游/用户显式要求）时报告必含独立核验小节——缺 = 自检未完成（禁交付）；
6. **消费回执（V1.4.0）**: 首次消费后回填（观测数据回流——技能效果实证的唯一通道）。
