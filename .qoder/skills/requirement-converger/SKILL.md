## 触发时机

- 用户提出**新需求/新项目/新功能**，需要形成可交给 agent 开发的需求文档时；
- 既有 PRD、聊天记录、散点材料 → 需要收束为标准需求文档包时；
- **长任务实验/长任务启动**：需要制作"唯一需求输入"包时；
- 需求文档**质量查缺/重写**：对照五标准逐项自检补全时；
- architect 规划前的**入参准备**（需求侧文档与该技能配套消费）；
- 既有需求包的**变更修订**（按 §变更处理 增量更新，不重跑全量）。

## 核心原则（CRITICAL · 第一性）

**需求文档 = agent 规划入参 API**——按 API 标准设计（**五标准 + 双红线**，共 7 条；与 C1-C8 检查项映射见 quality-checklist §0）：

```
【五标准（API 标准维度）】
🚨 显式 ── 契约/规则/枚举写死；"适当/友好/尽快"等模糊词必须转译为可判定行为描述
🚨 可枚举 ── 页面/表/端点/验收项全清单化；数量处处可对数（README速览 = 主文档清单 = 验收清单）
🚨 可验证 ── 每项验收有验证级别（L0构建→L1静态→L2冒烟→L3联调）与证据形式
🚨 关注点分离 ── 行为/数据/契约/设计分册制，按需加载（降上下文污染）；每事实一处权威
🚨 留白显式 ── "可自行设计 vs 必须对齐"逐项标注边界，防实现漂移与幻觉
【双红线（工程红线）】
🚨 单源化 ── 禁止多文档互相抄写；下游引用需求文档时携带版本/哈希
🚨 有据可查 ── 模板结构来自实证蓝本（见 §参考节）；本章节骨架不得凭空发明
```

> 反面教训（长任务实验实证）：配置无契约 → 联调期键位错位；验收未定义验证手段 → 运行时缺陷后置暴露。**配置也是接口；环境也是需求；凡拼接面皆契约。**

## 执行流程（S1-S4）

### S1 澄清采访（一次性输出完整问题清单）

1. **先盘点已有材料与数据源能力**：用户已提供的 PRD/记录/代码/口头需求 → 标记哪些问题已可作答（注明来源）；同时探测**项目数据库 MCP 可用性**（.mcp.json / 平台 MCP 配置——决定 I5 数据类问题的获取路径：可用→只读探查；不可用→问询/代码反推/降级，见 interview-guide I5「获取路径分流」）；
2. 按 [interview-guide.md](./references/interview-guide.md) 九类问题**一次性输出完整清单**（每问带编号 + 【必答/可默认（含场景标记）】 + 建议默认值）；**I5 数据类含"数据契约三问"**（关联关系/查询口径/历史表物理属性）；
3. 采访产出：**需求要素表**（问题 → 答案 → 将落入的文档节）+ **留白登记表**（未答/不确定项：可自行设计 / 必须对齐 / 待确认 + 影响面）；
4. 🚨 **中间态先行落盘**：S1 两张表先写盘再进 S2（生成中断时可据此续跑，见 §异常与边界处理）；
5. 🚨 禁止零散追问耗尽耐心——清单一次给全；用户不答的项按建议默认推进并登记留白，**不阻塞**。

### S2 结构生成（模板固化七亮点 + 三新节 + 数据契约三层）

按 [templates.md](./references/templates.md) 生成整个包。七亮点（长任务实验实证支撑 0-1 全栈的模板要素）必须逐项落位：

| # | 七亮点 | 落位 |
|---|--------|------|
| 1 | 分域可并行线索前置（最大效率来源） | README【可并行工作流划分线索】——**必须主动给出域拆分建议** |
| 2 | 关注点分离（分册制） | README / 主文档 / 附录A数据 / 附录B契约 / 附录C设计 |
| 3 | **数据契约三层**（字段级 + 关系级 + 口径级） | 附录A——数据从"猜"变"查"；关联关系与查询口径契约化；历史表加"使用面 DDL + 物理属性 + 核对脚本"专项（**按触发分级**，见 templates.md §4） |
| 4 | 契约显式化 | 附录B——端点/调用时序/一致性语义/幂等/安全通道/失败策略 |
| 5 | 可枚举交付物 | §一 建设范围表 + §八 验收清单（三处数量一致） |
| 6 | 负面清单先行 | 🚨 硬约束置顶（README + §二 + 独立负面清单节） |
| 7 | 状态机/枚举显式 | §三 枚举常量 + §四 各页面状态机 + 附录A 枚举字段 |

**三新节**（复盘缺口补丁，§2.4，必须生成）：

| # | 新增节 | 补什么缺口 |
|---|--------|-----------|
| ★1 | §九 **运行配置契约**（键名表 · 环境坐标 · 敏感值通道 · 覆盖优先级 · 失败策略 · **接线清单**[V1.5.0] · **失败策略实体化**[V1.5.0]） | 配置无契约导致的键位错位；"确认≠接线"；纸面策略不生效 |
| ★2 | §十 **环境预备清单**（连通性（含双通道探测） · 端口 · 账号/权限就绪标准 · 就绪判定汇总 · **就绪时效**[V1.5.0]） | 环境假设与实机不符；环境漂移 |
| ★3 | §十一 **验证手段矩阵**（验收项 × L0构建/L1静态/L2冒烟/L3联调 × 证据形式 × **环境形态行**[V1.5.0]） | 验收未定义"用什么级别验证"；策略无验证行 |

> 规则：**存在可运行环境时，验收面不得低于 L2**（启动冒烟）。**环境形态/降级行为属验收面（V1.5.0）**——契约声明的失败策略必须逐条有验证行（防"策略写了没人验"）。

**数据契约三层**（V1.3.0——附录A 按触发分级生成）：L1 字段级（必做）/ L2 关系级（查询表链涉及 ≥2 张表时——联查补全/跨表聚合或派生/历史表参与的关联）/ L3 口径级（聚合/派生/联查补全时——判定正反例见 templates.md §4.1）/ 历史表专项（历史建表接入时——使用面 DDL + 物理属性 + 可执行核对脚本，SQL 骨架见 templates.md §4.2）。**口径写死（语义层）、执行形态不锁（物理层）**——参考 SQL 允许实现侧等价改写，等价性以口径为准。

### S2.5 需求原型生成（条件环节 · V1.6.0——凡触及可见 UI 形态的需求）

> **触发判定（三问 · 第一性——锚点是"UI 形态"而非"页面数量/项目新老"）**：
> ① **有无 UI 面？** 无页面（纯 API/服务/数据治理）→ 跳过（自检报告声明 na）；有页面 → 进入 ②；
> ② **首次收束 or 增量变更？**
>    · 首次收束（整包生成）：页面 **≥10 或 UI 复杂度高**（多弹窗/多状态机/布局关键/需多方评审 UI）→ **生成全量原型**；<10 且简单 → 可选（登记用户决策）；
>    · 增量变更（走 §变更处理）：**触及以上可见形态**（新增页面 / 字段·按钮·布局·交互变更）→ **重生成受影响页面**；纯逻辑·校验·数据·契约·配置类变更（UI 不可见）→ **不触发**（原型不动）；
> ③ **需求来源（不决定是否触发——只决定素材路径）**：
>    · 老项目翻新 → 基于代码资产**重组探查**（页面元素/布局/触发逻辑）；
>    · **新需求/新项目 → 基于 §四 页面详述 + 需求材料直接生成**（无既有资产；UI 形态纯靠文字传递时原型价值更高）；
>    · 🚨 **两类来源均适用**——触发判定与来源无关。

**形态**：**to-be 原型**——按需求呈现的目标态页面集（素材路径见触发判定 ③）；纯静态 HTML/CSS/JS（可直接访问、零构建依赖、可离线打开）。

**生成方法论（实证沉淀）**：

| 原型要素 | 来源（禁凭空发明） |
|---------|------------------|
| 页面骨架（区块/布局） | §四 功能需求页面详述（老项目翻新场景叠加基线/逆向材料） |
| 字段/按钮/弹窗/校验 | §三/§四 规则与状态机（与文档逐项对齐） |
| 示意数据 | 现网实测数据或合规样例（含证据标注） |
| 样式/主题 | 目标工程技术栈设计系统（如有）——设计令牌**直译**，禁另起调色板 |
| 原系统缺陷/待改进项 | **不呈现**（负面清单为界——原型只含目标态） |

**资产结构**（落位 `{需求包名}/原型/`）：

```
原型/
├── index.html        # 总览（页面导航 + 使用说明 + 三红线声明）
├── p{N}-*.html       # 逐页原型（文件名 kebab-case，一页一文件）
└── assets/           # 共享 css/js（类名体系一次建立、多页复用；换主题只改令牌值）
```

- 每页底部**原型标注块**（依据章节 + 证据出处）——可追溯、可审计；
- 预览方式：本地静态服务或直接 file:// 打开（交付说明中告知用户）。

**🚨 三红线（使用与维护）**：
1. **单源化**——原型**不取代文档**：需求权威 = 需求包；原型与文档冲突时以文档为准（反向改原型须先回写文档）；
2. **防失真**——结构来自需求（禁发明新功能/新交互）；原系统缺陷不呈现；样式统一走目标设计系统（禁自由发挥）；
3. **版本绑定**——原型与需求包**同版本号交付**；需求包升版（§变更处理）须**同步重生成**受影响页面。

**S3/S4 联动**：页面密集型包的独立核验建议增查「原型 × 需求包逐页一致性」（页面数/字段/按钮/状态）；S4 交付语中标注原型资产清单与打开方式；下游 god/audit 可将原型作**页面级对照基准**（验收对照，非需求权威）。

### S3 质量自检（C1-C8）

对照 [quality-checklist.md](./references/quality-checklist.md) 逐项自检：C1 可枚举 / C2 可验证 / C3 无歧义 / C4 关注点分离 / C5 留白显式 / C6 版本单源化 / C7 任务书可生成性 / C8 数据契约完备性（**L1 必做 + 逐层判定**——触发层判缺、未触发的层不判缺；整项 na 仅限无数据面/V1.3.0 前旧包，唯一定义见 checklist §C8）。**任一项不过 → 修订后重检，禁止带缺口交付。** 报告尾部必须含 `REQ-STATS` 结构行（机器可断言——含 counts）。

**独立核验（条件触发 · V1.4.0）**: 包规模 ≥2 域 或 ≥2 外部端点（或下游/用户显式要求）→ 交付前由**独立方**（从零读取、不携带生成假设——本仓用 code-reviewer/audit 子代理）复核抽查位：C1 对数 × REQ-STATS counts / C5 留白真实性抽样 / C8 L1 字段级抽查 / REQ-STATS 诚实性（防自评虚高）；结论写入报告「独立核验」小节。**自检 ≠ 独立验证**（长任务实验：构建绿灯 ≠ 可运行）。

### S4 输出与交付

1. 输出目录 `{需求包名}/`（结构与各文件初稿，见 templates.md §0；**触及可见 UI 形态的需求另附 `原型/` 资产——见 S2.5**）；

## 变更处理（需求变更 / 文档修订——增量 SOP · V1.1.0）

> 原则：变更**不重跑全量**——按影响面定位重跑范围，改一处只需重检对应项（版本纪律 × 自检闭环）。

| 变更类型 | 重跑范围（S 步） | 复检项（C 判据） | 版本动作 |
|---------|----------------|----------------|---------|
| 新增/删除页面 | S2：§一 建设范围 + §四 页面 + §八 验收 + §十一 矩阵 | C1（三处对数）/ C2（矩阵覆盖） | 小版本递增 + 变更记录 |
| 全局机制/规则变更（§三/§六） | S2：对应机制节 + 受影响的 §四 页面要素 | C3（无歧义）/ C4（单源） | 同上 |
| 数据表变更 | S2：§五 + 附录A（三层同步——表/关系/口径） | C1（表对数）/ C4 / C8 | 同上 |
| 外部契约变更 | S2：§六 + 附录B + §十一 相关行 | C3 / C7（试写溯源） | 同上 |
| 配置键/坐标/通道变更 | S2：§九（+ §十 就绪标准联动） | C3 / C5（"必须对齐"项同步） | 同上 |
| 环境/验收面变更 | S2：§十 / §十一 | C2（级别下限声明） | 同上 |
| 留白项落定（必须对齐→已知） | 正文对应节 + 留白表更新（终稿） | C5（暗留白清零） | patch 递增 |

- **留痕强制**: 主文档「版本与变更记录」节逐行留痕 + 自检报告「修订记录」节同步；**禁止静默改正文**（无版本记录的修改视为违规）；
- **用户推翻前期答复**: 按上表定位重跑；留白登记表同步流转（待确认→已确认/必须对齐）；
- **大版本**（结构级变更：增删节/模板演进）: 全量 S2 重生成 + C1-C8 全量复检 + `REQ-STATS` 行更新。

## 异常与边界处理（S1-S4 执行中的失败路径 · V1.2.0）

> 总原则：**任何异常不得静默处理**——要么向用户呈现，要么登记留白，要么显式失败（禁用"悄悄取舍"）。

| 异常场景 | 处置 |
|---------|------|
| 用户材料自相矛盾（两份记录冲突） | **不静默取舍**——呈现冲突点与影响面，请求用户裁决；未裁决前按保守侧推进并登记"待确认"留白（标注冲突来源） |
| 用户推翻前期答复（包已生成需改） | 走 §变更处理——按影响面重跑 + 留白表状态流转 + 版本递增；**禁止**无版本记录地改正文 |
| 生成中断（S2 写到一半会话中断） | 从断点续跑：重读 S1 落盘的**需求要素表 + 留白登记表**恢复上下文（故 S1 产物先行落盘）；已生成文件按"文件完整性检查"逐个核验后继续 |
| 用户对建议默认值批量异议（≥5 项） | 逐项更新要素表 → 按 §变更处理 定位重跑；异议集中时建议重走 S1 清单（一轮给全） |
| 用户不回复（异步场景） | 按默认推进 + 登记留白 + **不阻塞**（S1 铁律）；交付物标注"基于默认值，待确认清单见留白表" |
| 关键材料缺失（如拿不到现网 DDL） | 登记"必须对齐"留白 + 写**就绪标准**（§十 模式）+ 附录A 历史表专项的"使用面最小集 + 核对脚本"（**绝不编造字段/坐标**——防幻觉纪律） |
| 需求超出技能边界（要求架构设计/接口冻结） | 明确告知边界（§能力边界声明），仅收束需求；设计类内容以"留白（可自行设计）"登记，交由 architect |
