# 方案支撑逻辑 (Solution Justification Logic)

> **核心原则**: 每个方案决策必须有现有信息做支撑，禁止凭空设计

---

## 🎯 方案支撑规则 (CRITICAL)

### 规则 1: 信息溯源

```
每个方案决策必须回答：

Q: 这个设计基于什么信息？
A: [必须引用具体的代码/文档/用户回答]

Q: 信息来源是什么？
A: [文件路径/对话记录/需求文档]

Q: 为什么这样设计？
A: [基于信息的推理过程]
```

### 规则 2: 决策追溯表

每个架构决策必须在报告中包含**决策追溯表**：

```markdown
## 决策追溯表

| 决策项 | 支撑信息 | 信息来源 | 推理过程 |
|-------|---------|---------|---------|
| 使用 Redis 缓存 | 用户回答: 数据量级 1000-10000 条/天 | Grill-Me Q3 | 高频访问场景需要缓存加速 |
| 分页查询 | 现有代码: KnowledgeService.findAll() | KnowledgeService.java:45 | 现有查询未分页，性能问题 |
| 角色级别权限 | 用户回答: 需要角色级别控制 | Grill-Me Q4 | 需要权限隔离 |
| API 路径 /api/knowledge/ask | 现有接口: /api/knowledge/* | .project_radar.json | 遵循现有路由规范 |
```

### 规则 3: 无支撑即挂起

```javascript
IF 方案决策无支撑信息:
    挂起，询问用户确认
    
IF 支撑信息来源不明确:
    挂起，要求先探查
    
IF 推理过程存在断层:
    挂起，要求补充中间推理
```

## 📊 方案分类与支撑要求

### A. 技术选型类决策

| 决策类型 | 必须支撑的信息 | 可接受的信息来源 |
|---------|--------------|----------------|
| 框架选择 | 性能要求、团队技能、现有技术栈 | 需求文档、团队背景、代码库 |
| 数据库选择 | 数据量级、查询模式、一致性要求 | 需求文档、数据分析、用户回答 |
| 缓存策略 | 访问频率、数据时效性、性能要求 | 性能测试、用户回答、监控数据 |
| 事务策略 | 一致性要求、并发量、性能要求 | 需求文档、业务规则、用户回答 |

### B. 架构设计类决策

| 决策类型 | 必须支撑的信息 | 可接受的信息来源 |
|---------|--------------|----------------|
| 分层设计 | 现有代码结构、职责划分 | 代码探查、文档分析 |
| 模块拆分 | 业务边界、依赖关系 | 需求文档、代码探查 |
| 接口设计 | 前端需求、现有接口规范 | 需求文档、代码探查、用户回答 |
| 数据流设计 | 数据来源、数据用途、数据规模 | 需求文档、用户回答、数据分析 |

### C. 实现细节类决策

| 决策类型 | 必须支撑的信息 | 可接受的信息来源 |
|---------|--------------|----------------|
| 字段命名 | 业务术语、现有命名规范 | 业务文档、代码规范、用户回答 |
| 状态机设计 | 业务流程、状态流转规则 | 需求文档、业务规则、用户回答 |
| 异常处理 | 异常场景、错误码规范 | 需求文档、代码规范、用户回答 |
| 日志记录 | 监控需求、审计需求 | 需求文档、运维要求、用户回答 |

## ⚠️ 常见问题与处理

### 问题 1: 信息不足以支撑方案

```markdown
❌ 错误示例:

决策: 使用 Qdrant 作为向量数据库
支撑: (无)

✅ 正确示例:

决策: 使用 Qdrant 作为向量数据库
支撑: 
  - 数据量级: 1000-10000 条/天 (Grill-Me Q3)
  - 查询模式: 向量相似度搜索 (需求文档)
  - 团队经验: 已有 Qdrant 使用经验 (团队背景)
```

### 问题 2: 支撑信息来源不明

```markdown
❌ 错误示例:

决策: 接口超时设置为 10 秒
支撑: 用户要求

✅ 正确示例:

决策: 接口超时设置为 10 秒
支撑: 
  - 用户回答: "对响应时间要求 < 10 秒" (Grill-Me Q5)
  - 性能测试: 向量检索平均耗时 3 秒 (性能报告)
```

### 问题 3: 推理过程断层

```markdown
❌ 错误示例:

决策: 需要 Redis 缓存
支撑: 数据量级 10000 条/天
推理: (直接得出结论，缺少中间推理)

✅ 正确示例:

决策: 需要 Redis 缓存
支撑: 
  - 数据量级: 10000 条/天 (Grill-Me Q3)
  - 访问频率: 高频查询 (需求文档)
  - 性能要求: < 1 秒响应 (Grill-Me Q5)
推理: 
  - 高频查询 + 数据量级大 → 需要缓存
  - 响应时间要求高 → 需要 Redis 加速
  - 结论: 使用 Redis 缓存
```

## 🚫 禁止行为

```markdown
🚨 以下行为严格禁止：

1. 无支撑信息的决策
   ❌ "我觉得应该用 Redis"
   ✅ "根据数据量级 10000 条/天，需要 Redis 缓存"

2. 支撑信息来源不明
   ❌ "用户说需要权限控制"
   ✅ "Grill-Me Q4: 需要角色级别控制"

3. 推理过程断层
   ❌ 决策 A → 决策 B (缺少中间推理)
   ✅ 决策 A → 推理过程 → 决策 B

4. 主观判断
   ❌ "可能需要缓存"
   ✅ "根据访问频率，确定需要缓存"

5. 假设性设计
   ❌ "假设用户需要..."
   ✅ "用户明确要求..."
```
