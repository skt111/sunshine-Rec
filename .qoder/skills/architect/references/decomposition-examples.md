# 大需求拆分 Few-Shot 对照示例

> **用途**: architect skill Step 1.5 复杂度评估的配套示例。当 AI 判断"是否拆分、如何拆分"时，对照本文件校准判断，避免两类方向性错误：
> - 反例 1 型错误：该拆没拆 → 上下文溢出、审计失焦
> - 反例 2 型错误：不该拆拆碎 → 原子性破坏、纯增成本

---

## 正例 1：该拆且拆对（复杂需求正确拆分为子 plan 群）

**需求**: "实现员工假期全流程管理（余额查询、申请、审批、历史记录、消息推送）"

**复杂度评分**:
```
跨端范围 2（前端 + Java 后端 + AI/Python 层 3 端）
文件影响 2（>8 文件）
新实体/表 2（3+ 张表）
业务规则 2（状态机 + 多系统联动）
安全影响 1（内部 + 外部南向接口）
总分 = 9 → 强制拆分
```

**正确拆分**:

| 子 plan | 范围 | 独立交付标准 | 依赖 |
|---------|------|-------------|------|
| task-A 假期余额查询 | 南向只读接口 + 卡片展示 | 余额查询接口可用，卡片渲染正确 | 无 |
| task-B 申请/审批状态机 | python 槽位 + java 事务编排 | 申请提交/审批流全链路闭环 | A（余额校验） |
| task-C 历史 + 消息推送 | 历史查询聚合 + 推送触发 | 历史可查，推送可触达 | A/B 数据 |

**父 plan**（task-0）: 记录总体需求、拆分逻辑、子 plan 列表、跨子 plan 依赖、集成验收标准。

**拆分后自检**:
- [x] 原子性: 每个子 plan 有独立验收标准
- [x] 依赖最小化: B 依赖 A，C 依赖 A/B（均 ≤2）
- [x] 无不可拆例外: 无跨子 plan 的强事务边界
- [x] 文件面可枚举（并行候选必查）: 各子 plan 文件面可枚举且两两不相交（本例：B/C 的文件面落在 A 的接口面之外，满足并行候选）
- [x] 共享资产时点: B/C 共用的接口面由 A 最先交付（共享资产最早波次——2026-09-15 复盘吸收）

---

## 反例 1：该拆没拆（复杂度被低估的后果）

**需求**: 同上"假期全流程管理"

**错误行为**: 复杂度评估为"中等（5 分）"→ 单 plan 直接实施

**后果链**:
```
一次会话 20+ 文件跨 3 端
→ 上下文窗口溢出（读到中段忘记前段契约）
→ 单端完成但未逐端验证（构建失败积压到最后一端）
→ 审计失焦（审计范围太大，P0 问题被淹没）
→ 返工成本: 全部重审 + 分段补验，总耗时 3 倍于正确拆分
```

**纠正**: 用评分卡逐维度打分（9 分），命中硬触发（3 子系统 + 3 表 + 3 功能点）→ 强制拆分。

## 反例 2：不该拆拆碎（原子性被破坏的后果）

**需求**: "修复假期余额查询接口日期参数不生效的 bug"

**复杂度评分**:
```
跨端范围 0（单端 Java）
文件影响 0（≤3 文件）
新实体/表 0（无）
业务规则 0（CRUD 修复）
安全影响 0（无）
总分 = 0 → 不拆分，单 plan 直接执行
```

**错误行为**: 拆成 3 个子 plan——"修 Controller" + "修 Service" + "修测试"

**后果链**:
```
同一调用链的原子修复被拆碎
→ 每个子 plan 无法独立交付（修了 Service 不修 Controller 等于没修）
→ 子 plan 间依赖 = 2+（互相等待，无法并行）
→ 索引膨胀 + 看板噪音（3 个卡片记录 1 个 bug）
→ 审计重复（同一段代码被审计 3 次）
```

**正确做法**: 单 plan 直接执行（评分=0），一次修复 + 测试 + 构建验证。

## 反例 3：拆对但文件面交叉（无法并行的拆分）

**需求**: "管理端新增两个页面：知识库页 + 导入页"（功能独立、可拆分）

**表面判断**: 拆为 2 个子 plan（两页各自文件面清晰）→ 拆分本身正确。

**并行校准（第 4 问）**: 两页共用同一共享组件（如知识表单抽屉）与路由注册文件——**文件面相交** → 标注：共享面收归单一 owner 或先行串行（禁止两 worker 各改一半）。

**共享资产时点（第 5 问）**: 两页共用的共享组件（如知识表单抽屉）若属新建/改造件——须安排在最早共同波次（或串行前置段）先行交付，两页子 plan 再挂其依赖；防"晚到"导致引用方阻塞断链（2026-09-15 复盘吸收）。

**正确做法**: 拆分保留，但共享面（组件/路由）先冻结（单一 owner 先行）后再并行两页；无法收归则串行。反例警示：**功能独立 ≠ 文件面独立**——并行前必过文件面矩阵（god --parallel 阶段 A）。

## 判定速查表

| 场景信号 | 判定 |
|---------|------|
| 评分 ≥7 或命中任一硬触发 | 强制拆分 |
| 评分 4-6 或命中 ≥2 软触发 | 建议拆分，询问用户 |
| 评分 ≤3 | 不拆分，简化路径 |
| 同一调用链的原子修复 | 永不拆分（如 bug 修复、单接口改动） |
| 事务边界跨多个子功能 | 合并为单 plan（不可拆例外） |
| 功能独立但文件面相交（共享组件/路由/配置） | 拆分保留，共享面收归单一 owner 先行；无法收归则串行（并行前必过文件面矩阵） |
