# Architect Skill - 架构师模式

需求到图纸的转换器。基于第一性原理进行规划与拆解。

## 🎯 核心约束 (Core Constraints - CRITICAL)

```
🚨 未探查即挂起 ──── 未扫描现有系统 → 挂起询问
🚨 信息缺失即挂起 ── 缺失信息不明确 → 挂起询问
🚨 方案需证据支撑 ── 每个建议必须引用现状扫描的具体发现
🚨 严禁修改代码 ──── 本模式仅规划，禁止任何业务代码修改
```

## 📋 执行流程

> **全景读取豁免声明**: 本 skill 做规划决策（拆分判定/依赖分析/评分卡 D 域）时**需要读取全量 plans.json**（architect 是全局决策者，非执行型）；该豁免与 A 阶段"读取切片"约束互补——执行型 skill（god/sandbox/audit/recovery）切片读，规划型（architect）全景读。

🚨 **强制顺序约束 (CRITICAL)**:

```
正确顺序: 意图入参检查(0.5) → 需求分析/意图对齐(1) → 复杂度评估(1.5) → 探索 → 现状扫描 → 路径优化 → 方案贯通审计 → 输出前自审三查 → 评分卡 → 规划输出
           ↓            ↓          ↓        ↓           ↓            ↓            ↓        ↓        ↓
         不可跳过     不可跳过   可选      不可跳过    不可跳过     不可跳过     不可跳过 不可跳过  最后输出

❌ 错误行为:
- 复杂度评估未做就拆分/不拆 → 🚨 挂起（拆分判断必须量化）
- 未建档意图直接规划（复杂度 ≥2 新需求无 intent 文档）→ 🚨 挂起建档（Step 0.5——intent 是入参契约）
- 涉及建表但未做数据源确认 → 🚨 挂起（禁止默认数据源）
- 现状扫描未完成就输出规划 → 🚨 挂起
- 路径优化无证据就输出规划 → 🚨 挂起
- 方案未过贯通审计就输出规划 → 🚨 挂起
- 自审三查未过就输出规划 → 🚨 挂起（输出前闸门）
- 评分卡未达绿灯就输出 plan → 🚨 挂起（质量门禁）
- 规划输出后再补充扫描 → 🚨 无效，必须重来

违反此规则 = 架构师模式失效，必须重置流程
```

### 0. PLAN 加载判断

| 场景 | 加载? | 理由 |
|-----|------|------|
| 全新需求 | ❌ | 避免旧上下文污染 |
| 修改现有任务 | ✅ | 需了解当前进度 |
| Bug 排查 | ⚠️ | 视是否涉及正在开发的任务 |

### 0.5 意图入参检查 (NEW · task-103 W1，2026-09-09)

**定位**: 意图层（intent 文档）是 architect 规划的**入参契约**——在进入 §1 前先确认"已捕获、可审查、已确认"的意图存在，否则挂起建档。

```
三态判定:
├─ 已有 intent 文档（.qoder/intents/ 命中，plan 登记时引用）
│   → 状态: status ∈ {confirmed} → 以 intent 为入参基线，进入 §1（对齐后继续）
│   └─ status = draft（未确认）→ 挂起：先让发起者确认再规划
├─ 无 intent 且 前置预筛 ≥2（quick triage——复杂度尚未正式评估，用 §1.5 软触发维度粗判：
│   预计文件 >8 / 涉及 ≥2 子系统 / 建表 / 外部对接，任一命中即 ≥2）
│   → 先执行捕获（采访见 02-clarification 澄清产物协议）→ intent 落盘 .qoder/intents/ →
│     发起者确认（status=confirmed）→ 挂起等待确认后回到本步 → 进入 §1
└─ 轻量需求（预筛 <2）→ 直通（免建档，简化路径；02 澄清仍可按需执行）
```

**双闸容错（防执行卡死）**: 0.5 预筛为粗判；§1.5 正式复杂度评估若 <2 → **回退直通**（补记"轻量豁免，免建档"），不强制回补 intent。

**产物约束**: intent 文档按 `.qoder/intents/INTENT-SPEC.md` QUALITY 五判据写作（起点契约——禁技术方案）；域名称对齐 domain-index.json（未建档记域缺口）。

**需求包衔接（条件触发 · 2026-09-16）**: 若本需求已经过需求收束（requirement-converger）产出需求包 → 包即**需求侧基线**：intent 建档/更新时引用包与版本（`需求包: {路径} v{X}`）；后续规划按"包 → intent"引用链消费（携版本/哈希，见 §4 证据要求），**禁止回写或复制包内容**；**入参核对（V1.4.0）**: 消费前校验自检报告 `REQ-STATS`——`fail` 拒收回退收束；`conditional` ⚠️ 项并入挂起候选；`pass` 直通；**缺行/不可解析视同 `fail`；历史代际包按 checklist 兼容条款处理**；捕获采访（三态判定"无 intent"支）以包为输入基线、**不重复问包内已答项**；包缺失时不适用（常规三态判定继续）。

### 1.5 复杂度评估与拆分判定 (NEW - CRITICAL)

**定位**: 大需求拆分必须量化。凭感觉拆分会产生双向错误（该拆没拆→上下文溢出；不该拆拆碎→原子性破坏）。

**复杂度评分卡（5 维度 × 0-2 分 = 0-10 分）**:

```
┌─ 跨端范围: 0=单端 / 1=2端 / 2=3端+
├─ 文件影响: 0=≤3 / 1=4-8 / 2=>8
├─ 新实体/表: 0=无 / 1=1-2 / 2=3+
├─ 业务规则: 0=CRUD / 1=状态机+分支 / 2=多系统联动（harness 工程域类比: 协议面跨≥3 消费方联动按 2；单点文档条款按 1——task-108 W5 注）
└─ 安全影响: 0=无 / 1=内部 / 2=外部接口+认证

判定:
0-3 分  简单 → 单 plan，简化路径
4-6 分  中等 → 单 plan + 强制沙盘
7-10 分 复杂 → 强制拆分（或用户显式批准不拆，需记录理由）
```

**硬触发（任一即拆，无讨论余地）**:
- 涉及 ≥3 个子系统
- 新建 ≥3 张数据库表
- ≥3 个独立可交付功能点
- 外部系统对接（契约先行，必须独立成 plan）

**软触发（≥2 条建议拆，询问用户）**:
- 涉及 2 个子系统
- 新建 1-2 张表
- 2 个可交付功能点
- 工作量 >8 文件

**拆分质量自检 5 问（拆后强制）**:
```
[ ] 原子性: 每个子 plan 可独立交付、有独立验收标准？
[ ] 依赖最小化: 子 plan 对其他子 plan 依赖 ≤2？（>2 重新切分）
[ ] 不可拆例外: 存在事务边界/原子操作强耦合？（存在则合并回父 plan）
[ ] 文件面可枚举（并行候选必查）: 各子 plan 文件面可枚举且两两不相交？（不可枚举/相交 → 标注串行段；目标为并行开发时此问强制——衔接 15-parallel-dev.md / god --parallel）
[ ] 共享资产时点: 被 ≥2 子 plan 引用的共享资产（组件/契约/工具/表）已安排在最早共同波次或串行前置段先行交付？（未定 → 标注资产交付波次——防引用方阻塞断链；2026-09-15 复盘吸收）
```

**Few-shot 校准**: 判断犹豫时对照 [references/decomposition-examples.md](./references/decomposition-examples.md)（正例/反例/判定速查表）。

### 1.8 探索与信息收集 (NEW - 可选，复杂度 ≥4 或涉及建表时推荐)

**定位**: 为 plan 提供数据建模、逻辑流转等引用信息。让 AI 从"猜"变为"查"——数据源是探索的第一信息约束，缺省即猜测。

**Step A - 数据源确认（必须询问用户，禁止默认）**:

```
## 📋 数据源确认
1. 生产库（只读）: 确认使用现有 MCP 配置？
   - A) 直接查询   B) 先出表清单供核对再查
2. 测试库: 是否有配套测试库？（是否可写，用于 DDL 验证）
3. 权限边界: 可查询 schema 范围？
4. 敏感数据: 结果含敏感字段时是否需脱敏展示？
```

**Step B - 表清单核对闭环（防探查跑偏）**:

```
Oracle MCP 查 all_tables 过滤候选 → 输出核对表：
| 候选表 | 用途判断 | 相关? |
|--------|---------|-------|
| PS_LEAVE_REQUEST | 申请主表 | ✅ |
| PS_EMP           | 员工主数据 | ❌ 已有链路 |
→ 用户确认/纠正后才进入列级 DDL 探查
```

**Step C - DDL 建模闭环（防字段级幻觉）**:

```
产出规范（新表写入 `.qoder/plans/explorations/{topic}-{date}-ddl.sql`）：
- CREATE TABLE + COMMENT ON（表注释 + 每列注释）
- 约束: PK/FK/UNIQUE/CHECK 显式声明
- 索引: 每条附查询路径理由
- 来源标注: 每个字段注明"来自 XX 表 XX 列"或"新增字段（需求 §X 定义）"
```

**产出**: `.qoder/plans/explorations/{topic}-{date}.md`（数据模型/实体关系/状态流转/API 清单/开放问题），plan 通过 frontmatter `exploration` 字段引用（基准目录 `.qoder/plans/explorations/`，validate-plans.js 会校验引用文件存在性）。

**闭环**: 探索(查真实表) → 建模(DDL 全注释) → plan 引用 → God 实施直接用 → Audit 核验实现与 DDL 一致。

### 1.9 spec 生成（intent → 需求基线 · S5 消费流水线——域/资产/风格/表治理注入；复杂度 ≥2 必走；<2 由 §2 现状扫描兜底；门槛条款 2026-09-07 回填 spec §S5；定位升级 task-105 W2 2026-09-09）

**定位**: 本步是 **spec 生成器**——输入 = intent 文档（Step 0.5 校验 status=confirmed）；产出 = plan 详情「需求基线」yaml = **spec 契约**（设计约束层：域/复用/风格/数据，回答"怎么做"；意图层回答"为什么/做什么算对"——每层只加自己的信息，**不回写意图**）。新需求规划前先消费领域档案（business-architecture/domain-index）与资产目录（asset-catalog/style-profile），把"新实现 vs 复用"从凭感觉变为**证据裁决**；产物写入 plan「需求基线」节（机器可校验，V-A7 validate-plans 解析）。生成质量判据见 **references/spec-quality.md（Q1-Q5）**。意图澄清由 §1 意图对齐/02-clarification 承接（本步自 §1.8 后直接进入域定位）。

**治理注入清单（五注入点——spec-quality.md 为判据权威）**:

| 注入点 | 治理载体 | 对应步骤 |
|--------|---------|---------|
| 域一致性 | domain-index/business-architecture（按节引用，不整本） | Step 1 域定位（四态） |
| 资产复用 | asset-catalog + REUSE/PARTIAL/NEW 三态 + A1/A2 确认 | Step 2 资产调研 |
| 风格规范 | style-profile（轻量索引）+ 端级规则（引用不复制） | Step 3 风格匹配 |
| 数据真实性 | 表清单 T1 确认 + DDL 注释闭环 | Step 4 表/数据确认 |
| 可机器校验 | V-A7（yaml 无 REPLACE_ME/裁决有据/确认记录齐全） | Step 5 基线写盘 |

**Step 1 - 域定位**: 提取需求域词 → 查 `domain-index.json`（CONTEXT_DIR 内）命中域 → 读 `business-architecture.md` 命中域节（**按节引用，不整本加载**——防上下文污染）。四态处理：
- 命中且节非空 → 读节（引用 profileSection 锚点）
- 未命中且涉业务表 → 记“域缺口”，走 §1.8 探索补齐（§1.8 已产出 T1 则复用其记录，不重复确认）
- **命中但节为空 / index 锚点失效 → 🔴 强制挂起询问**（禁静默降级/读邻节——S7 P1-11，与 V-A6 section 锚点校验联动）
- 档案整体缺失 → 跳过 + 基线注明“档案缺失”（不阻断——披露优先，缺口回流 inventory）

**Step 2 - 资产调研（三态裁决 + A1 确认）**: 能力词 × `asset-catalog.json` 命中条目 → 三态裁决：

```
| 态 | 条件 | 动作 |
|----|------|------|
| REUSE | confidence ≥ medium ＋ 能力词匹配（含命中理由+反例检查输出）＋ binding 兼容（pure 直接复用；business 需抽提 → 降 PARTIAL） | 输出 A1 确认卡（🔴 强制，人裁决后落基线；空 catalog 直通豁免）——确认后方案引用条目（路径/用法/坑）；需改造标“扩展” |
| PARTIAL | 部分能力命中 或 binding 需抽提 | 复用 + 增量设计（抽提边界）——一律进确认卡 A2 |
| NEW | 无命中/全 legacy（catalog 为空直通免噪音） | 输出 A1 确认卡（🔴 强制；空 catalog 直通豁免）——确认后新实现 + plan 登记“资产缺口”（缺口回流 catalog = 活文档闭环） |
```

### 4. 路径优化与证据要求 (NEW - CRITICAL)

评估实现路径时，**每个建议必须有证据支撑**：

| ❌ 无证据支撑 | ✅ 有证据支撑 |
|-------------|-------------|
| "推荐路径 A 因为更简洁" | "推荐路径 A，现状扫描发现已有 `UserService.java` 可复用" |
| "这是最佳实践" | "现状扫描显示数据库已有 `created_at` 索引，可直接利用" |
| "我认为应该这样做" | "根据 `API 契约 v1.2`，接口已定义..." |

**禁用理由**: "更简洁"、"最佳实践"、"我认为" 等无支撑的主观判断。

**证据形式要求 (CRITICAL)**:

| ✅ 有效证据 | ❌ 无效证据 |
|-----------|-----------|
| 文件名 + 行号: `UserService.java:45` | "最佳实践" |
| API 契约引用: `API 契约 v1.2 - /api/user/login` | "更简洁" |
| 配置引用: `application.yml:23` | "我认为" |
| 依赖引用: `pom.xml:56` | "经验表明" |
| 现状扫描发现: "已存在 `UserService`" | 无具体引用的泛泛而谈 |
| 需求/规格引用: `需求文档 v2.0 §2.2`（外部文档引用须携版本/哈希） | "任务书里说过"（无版本可核） |

> **外部引用版本纪律（2026-09-15 复盘吸收）**: 引用外部文档（需求/规格/任务书）的特定条目时须携带版本或哈希；核对时发现引用条目不存在/版本不一致 → 挂起并登记差异（防多文档交叉引用语义漂移）。

🚨 方案建议必须附带有效证据，否则挂起

### 6. 方案贯通审计 (NEW - CRITICAL)

> **定位**: 输出前最后闸门。§2-§4 是**输入侧**检查（扫描充分/信息完整/证据支撑），本节是**输出侧**检查——方案自身作为一张图（节点=数据对象/流程节点, 边=流转/依赖），逐点核验整张图可落点、可走通。
> **执行细则见** [./references/coherence-audit.md](./references/coherence-audit.md)（审计表模板、逐层对表方法、系统边界重点、happy-path 陷阱）。

**方案未过审计 = 禁止输出规划**，必须回到对应阶段修正后重审。

#### A. 覆盖审计 (需求 ↔ 方案)

```markdown
[ ] 每条需求都有对应设计落点 (无遗漏需求)
[ ] 方案不存在需求外的设计 (无过度设计)
```

#### B. 数据贯通 (方案 → 现状)

```markdown
[ ] 存在性: 方案引用的每个数据对象在现状中真实存在 (字段/结构/接口/存储)
[ ] 一致性: 同一数据在链路每段定义一致 (命名/类型/语义/格式/单位)
[ ] 闭环性: 每个数据有源有汇 — 有读必有写 / 有写必有读 / 输出可追溯至生产点
[ ] ★ 系统边界: 数据穿过系统边界处 (外部调用/异步/回调/跨子系统) 字段映射完整, 超时/重试/幂等有落点
```

#### C. 逻辑贯通 (方案 → 现状)

```markdown
[ ] 连通性: 主流程每节点有后续且可达终点, 终点可追溯回需求起点 (无死路/无悬空步骤)
[ ] 完备性: 异常/边界/取消/失败路径同样闭环 (非主路径单列检查, 禁止 happy-path 审查)
[ ] 自洽性: 规则无矛盾, 分支无重叠/无歧义, 流程有终止条件
```

**审计不通过的处理**: 输出审计表 (见输出格式), 标注断链点 → 回到对应阶段 (扫描/路径优化/契约) 修正 → 重审 → 通过后才允许输出 plan（写入 `.qoder/plans/{id}-{slug}.md` + 更新 `plans.json`）。
