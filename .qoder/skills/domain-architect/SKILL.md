# Domain Architect Skill - 域档案合流模式

> 版本: V1.1.0 ｜ 2026-09-22 ｜ 依据: Spec v0.2 S4.2（披露优先/多信号/置信度分级）+ S6 确认协议 + 收敛设计（business-architecture 单权威）+ 增量更新模式（外部体系吸收）
> 定位: S4 档案供给的**域层执行器**（asset-catalog/style-profile 由 inventory 命令供给；域档案由本技能执行——交互本质（披露+审批）不适配纯 CLI）

## 触发时机

- 老项目迁 harness：领域文档欠账补全（S16 场景）
- 既有 business-architecture.md 合流重构为 v0.2 域节格式（agent 类仓 dogfood）
- 新仓首建域档案（无 BA）
- inventory 输出 domain-index 缺失提示后（P2-10 缺口补全）
- **plan 收尾时域行为变化（归档核验前）——增量更新模式（delta 并入；正常路径；兜底=归档核验倒逼补做）**

## 核心原则（CRITICAL）

```
🚨 披露优先不可倒置 ──── 权威锚点（域划分/表归属）只能人给或取自已有人写权威文档；扫描只辅助
🚨 低置信不进正文 ──── 仅命名推断的映射落"待人工确认清单"，绝不进域节权威位
🚨 单权威合流 ──── 产出合入 business-architecture.md（按域节）；禁止另起 domain-profile 双写
🚨 活文档保护 ──── 已存在 BA 不整体覆盖——按域节增量并入 + 版本/日期
```

## 执行流程（四阶段）

### Phase 0 - 披露源识别（最高置信锚点）

按序取第一个可用披露源（不重复询问）：

```
1. 用户直接给域词/核心表清单/DDL 路径/状态流程点名（grill-me 设计树追问）
2. 既有权威文档 = 人写披露：business-architecture.md / api-contract / README 业务节 / 既有 CLAUDE.md 约定
   → 提取域划分候选（文档标题/业务章节/表名出现聚类）
3. 无任何披露 → 声明降级（Phase 1 全输出标 low 置信，Phase 2 必须审批）
```

**产出**: 域清单草案 `[{域词, 关联表候选[], 关联代码路径[], 披露源}]`

### Phase 1 - 自主扫描（降级路径 · 多信号投票）

对每个候选域/表执行信号扫描（信号可靠性排序）：

```
DDL/表结构（最可靠）→ @TableName/@DS 注解 → mapper XML resultMap/INSERT 表名 → 类名蛇形/命名推断（最弱）
```

- **多信号投票**: 单一信号不裁决；≥2 信号同向才给 high/medium；仅命名推断 → low
- 每域节要素: 核心实体×表×数据源（@DS 归属）/ 实体关系（FK/注释）/ 状态机（枚举+流转+权威字段）/ 关键 Service 入口（方法级锚点）/ 命名口径（防 taskName/task_name 分裂）
- 低置信结果**不入正文** → 落"待人工确认清单"

**产出**: 候选域节（带置信度与证据来源）+ 待确认清单

### Phase 2 - 用户审批（确认卡——S6 协议）

对裁决点输出确认卡（逐项）：

```
🔎 确认卡 <id>（类型: D1 域划分 | A1 表归属 | T1 状态机权威）
- 发现: [扫描证据/文档证据]
- 推断: [域归属/状态机裁决建议]
- 影响面: [涉及表/Service/消费方]
- 选项: A) 采纳 B) 修正（用户给正确值）C) 挂起待查
- 推荐: A（证据充分时）——AI 提议、人类裁决
```

- 🔴 必批项: 域划分（D1）、高影响表归属（A1）；🟡 批量批: 低影响确认清单
- 防伪: 记录回显文本 + 时序（V-A8）；审批记录写入计划/交接文档
- 驳回 → 按修正值重扫该域（增量，不整盘重来）

### Phase 3 - spec 结构化输出

```
1. business-architecture.md（CONTEXT_DIR 内）:
   - 不存在 → 新建（按域节骨架 + 待挂载清单）
   - 已存在 → 域节增量并入（活文档保护：保留既有章节，域节标准化追加；整体结构收敛为按域节）
2. domain-index.json: { domains: [{domain, keywords, profileSection, codePaths, updated}] }
   - 已存在 → 增量（新域追加/旧域 updated 刷新）
3. 自校验: verify V-A6 通过（profileSection 锚点在 BA 可解析 / codePath 存在 / 无 domain-profile 残留双写）
```

**产出**: BA 域节 + domain-index.json + 审批记录（确认卡汇总）

**增量更新模式（delta 并入——V1.1.0，外部体系吸收）**

> 适用: plan 收尾时域行为变化（归档核验前——触发时机节第 5 条）——日常增量维护场景（区别于首建/合流的全量四阶段）。

变更源（plan 行为变化——plan 详情「验证证据」节 + 需求基线）以 `ADDED/MODIFIED/REMOVED` 小节声明变更量 → **合并三步**:

1. **读源**: 读变更源提取 delta 声明
2. **应用 delta**: 按 delta 并入对应域节——保留原文语义骨架，变更点就地标注（`[ADDED]`/`[MODIFIED]`/`[REMOVED]` 或等价标记）
3. **版本/日期刷新**: 域节版本/updated 刷新——**声明落盘载体 = 域节变更点标注 + 版本/日期刷新本体（不新建 delta 文件/目录）**

**与"活文档保护"衔接**: 增量并入不破坏既有语义骨架；`REMOVED` 不整节删除（留变更痕迹）。**双路径**: 正常 = plan 收尾时（归档核验前）按本模式执行；兜底 = 归档核验（SOP Step 1.5）发现域行为变化未合并时倒逼补做（恢复路径: 回本模式补做 → 再提归档）。
