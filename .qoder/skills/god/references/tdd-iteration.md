# TDD 迭代方法论细则（行为驱动 + 上下文感知 + 垂直切片）

> **定位**: god SKILL "TDD 迭代协议"节的配套细则（渐进式引用，SKILL 不内联全文）。
> **融合来源**: 通用行为驱动 TDD 方法论 × 本项目执行骨架（god V2.5.1）+ 项目防幻觉护栏（真实消息结构/触达本体）。
> **适用**: 执行策略表映射为 TDD 迭代的任务（新功能 + 有测试 / Bug 修复 + 有测试）。

## 一、上下文感知（写测试前必读，防"领域文盲测试"）

测试不是孤立的技术活动——测试名、接口词汇、断言语义必须与项目领域语言对齐：

| 上下文源 | 位置 | 用途 |
|---------|------|------|
| 业务架构与领域词汇 | `.claude/context/business-architecture.md` | 领域模型、状态机、业务规则的语义权威 |
| 总纲词汇表 | 端级规则 §4 词汇表 / 子端 CLAUDE.md 词汇节 | 术语口径（如业务术语的接口/字段命名习惯） |
| 架构决策记录 (ADR) | `.claude/context/` 架构决策文档、`docs/` 决策报告 | 尊重既有决策（如"测试必须使用真实消息结构"等经验约束） |
| API 契约 | `.claude/api-contract/`（经 `.project_radar.json` 定位） | 接口词汇与字段语义的测试基准 |

**对齐要求**:
- 测试类名/测试名使用**领域术语**（如 `XX申请提交后状态流转` 而非 `testFunctionA`），断言消息也用业务词汇
- 接口测试的字段名/枚举值必须与契约一致（驼峰/下划线、枚举拼写逐字符对齐）
- 若测试设计与既有 ADR 冲突 → 挂起说明，禁止静默违反

## 二、测试规划前置（Step 0: PLAN）

写任何断言前，先完成 3 项规划（输入 = plan 详情的场景矩阵 01 §4.1）：

```
[ ] 确认行为: 本测试要验证哪个用户可观察行为？（不是哪个函数）
[ ] 确认界面: 通过哪个公开 API/入口触达该行为？（Controller 端点 / 公开方法 / 路由）
[ ] 可测试性设计: 该行为是否可独立测试？依赖如何注入/隔离？不可测 → 先重构出测试缝，再写测试
```

**规划产物**: 每轮 RED 前在检查点记录"本轮行为 / 入口 API / 预期断言"。

## 三、行为中心测试（黑盒优先，防"实现耦合测试"）

| 原则 | 说明 |
|------|------|
| **通过公开 API 验证行为** | 测试走 Controller/公开方法/路由，不测私有实现细节——内部重构后测试应保持不变 |
| **集成式优先** | 能通过公开 API 端到端验证的行为，优先集成测试；仅当公共 API 无法表达时才用单元级（且仍测公开方法） |
| **测试-重构不变性** | REFACTOR 步骤后**测试代码零修改**（若重构需要改测试 = 测试耦合了实现细节，是坏味道） |
| **断言行为而非步骤** | 断言"返回了什么/状态变成了什么"，不断言"内部调用了哪个私有方法" |

**与项目护栏的关系（互补）**:
- 行为中心解决"测什么"（黑盒行为）；项目护栏解决"数据/对象真实性"（真实消息结构 + 触达被测对象本体）——两者叠加才构成完整防幻觉测试：既测对行为，又用真实数据测真实对象。

## 四、垂直切片（一测试→一实现→重复，防"水平切片"）

```
✅ 垂直切片（正确）:                     ❌ 水平切片（错误）:
  RED-1 → GREEN-1 → REFACTOR             写全部 10 个测试
  RED-2 → GREEN-2 → REFACTOR             → 再写全部实现
  ...（每次一个行为闭环）                 → 最后一起跑
```

**水平切片的危害**: 测试先行写完但实现最后落地 → 中间态无法验证、失败定位模糊、测试与实现大面积失配 → 脆弱且行为敏感的测试套件。

**垂直切片的执行规则**:
- 一轮 = 一个行为从 RED 到 GREEN（最小实现仅满足该行为）
- 重复直到场景矩阵的行为清单逐项闭环
- 边界用例（空值/极限/并发/权限）作为后续独立轮次（RED）加入，非一次性堆砌

## 五、重构指南（仅全绿后应用）

REFACTOR 步骤仅在**当前轮测试全绿**后执行，按以下方法优先级：

```
1. 复制提取 (Duplicate → Extract): 消除复制粘贴（提取方法/常量/类）
2. 模块加深 (Deepen Modules): 隐藏实现细节，模块只暴露稳定接口
3. SOLID 检查: 
   - S 单一职责: 类/方法是否只做一件事
   - O 开闭: 新增行为能否不改动既有分支（扩展点 vs if-else 堆叠）
   - L 里氏替换: 子类/实现是否可无差别替换
   - I 接口隔离: 消费者是否只依赖其需要的部分
   - D 依赖倒置: 依赖抽象还是具体实现
```

**约束**:
- 🚨 重构后必须重跑测试确认全绿（测试应零修改，见 §三）
- 🚨 重构禁止与 GREEN 混在同一变更里（先绿后重构，两步分离）
- 重构可跳过（跳过须注明原因），但跳过不豁免"复制提取"类的高价值项

---

## 六、与验证体系衔接（引用 god SKILL 主体）

- 循环 5 步（PLAN→RED→GREEN→REFACTOR）+ 迭代状态记录 + 熔断规则见 god SKILL "TDD 迭代协议"节
- 全部轮次结束后进入 god 阶段 4（构建 + 测试 + 场景三路由验证）
- 失败计数: 同一测试失败 ≥2 次（GREEN 修复尝试起算，RED 确认失败不计入）或总迭代 ≥5 轮 → 熔断（plan 置 blocked）
