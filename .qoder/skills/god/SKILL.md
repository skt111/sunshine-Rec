> **版本**: V2.9.1

## 🚨 核心原则

| 原则 | 说明 |
|-----|------|
| **签名验证** | 执行前必须验证沙盘/审计报告签名，确保由独立 Agent 签发 |
| **检查点** | 每个关键阶段完成后设置检查点，记录进度 |
| **挂起确认** | 每阶段完成后询问用户是否继续，支持手动挂起（**自治授权下按「自治授权语」条款——落账代替询问**） |
| **简单至上** | 模板/示例/伪代码外置，仅保留核心流程 |

## 🎯 参数说明

| 参数 | 说明 | 示例 |
|-----|------|------|
| `--resume {planId}` | 续接指定任务 | `/god --resume task-93` |
| `--urgent` | 紧急 Hotfix 模式 | `/god --urgent` |
| `--parallel {parentId}` | 并行执行模式（多 worker fan-out/fan-in，单会话内） | `/god --parallel task-100` |

**`--resume` 处理流程**:
1. 加载检查点: `.qoder/skills/audit/checkpoints/checkpoint-{planId}-*.md`（按 updated 取最新一份；写路径规范 `checkpoint-{planId}-{ts}.md`）
2. **读取检查点「执行账本」尾行 + plan 详情「修复轮次记录」节**——输出 blocked/超限状态与最近裁决（断点定位依据；账本规范见「检查点管理」）
3. 加载 plans.json 中该 plan 的行与交接状态（plan 详情"跨端交接"章节）
4. 输出续接信息（含账本断点与修复轮次）
5. 自动继续执行

详见: `.claude/templates/resume-prompt.md`

**`--parallel {parentId}` 处理流程**:
1. 校验父 plan（children ≥2，**父沙盘凭证 pass（拆分级别绿灯）**）；盘点子 plan 沙盘凭证（已有复用 / 无则阶段 B 补跑）；**启动动作**: 父→in-progress + activePlan 指向父（children 出队时批量 active→in-progress）；单 plan 场景回常规流程
2. **文件面矩阵核验**（两两不相交——阶段 A 闸门）；划分 wave（强依赖后置）
3. 按 `references/parallel-orchestration.md` 执行阶段 A-G（并行沙盘 → worker fan-out → CR 仲裁 → auditor 流水线 → 汇聚验证 → 收口）；**五阶段语义映射**（阶段 1=父凭证+子凭证产出/复用，阶段 4=汇聚验证——见编排 §0）
4. 并行模式为单线程 5 阶段的**叠加变体**——资产写收口与审计独立性硬约束见 `.qoder/rules/15-parallel-dev.md`

详见: `references/parallel-orchestration.md`

## 📋 执行前自检清单

### 1. 签名验证（必须）

**定位报告（A 阶段：按 plan 精确匹配，禁全局最新）**:
- 沙盘报告: 在 `.qoder/skills/sandbox/reports/` 中匹配**当前 plan id** 的报告——命名含 `{planId}`（规范 `{YYYY-MM-DD}-{planId}-{topic}-沙盘审计.md`）或 frontmatter `plan_id` 等于当前 plan；多份按 updated 取最新；无匹配 → 🟡 提示"该 plan 无沙盘报告"（存量无 planId 报告不参与匹配，历史豁免）
- 审计报告: `.qoder/skills/audit/reports/` 中匹配 `audit-{planId}*.md`（历史路径 `.claude/audit/reports/` 已废弃）

**签名校验说明（存量豁免）**: 2026-09-02 前落盘的存量报告（无 signatures/plan_id frontmatter）视为历史产物，校验降级为"文件存在且含通过/不通过结论"；新规范报告（含 plan_id + signatures frontmatter）按下方规则严格校验。 存量报告**不参与当前 plan 的精确匹配**（无 plan_id 键）；若当前 plan 确无新规范报告，仅存量报告可用 → 视为凭证缺失（🟡 + 用户显式豁免），**禁止**以存量报告充当新凭证。

**结构行解析（task-106 W3 · 2026-09-10——三态显式映射）**: 验签按报告形态三态消费：
- **a) 含 REPORT-STATS 结构行（新规范）** → **机器解析优先**: 读取 `REPORT-STATS: plan_id=… P0=n P1=n P2=n VERDICT=…`（取最后一条匹配）；sandbox 报告 VERDICT=pass 即绿灯；**audit 报告按 P0=0 且 P1=0 双条件判定**；结构行自洽（P0>0 不得 pass）由 validate §6.8 前置保证
- **b) 无结构行但含 frontmatter（过渡期报告——2026-09-02 ~ 09-10）** → 签名表 + **人工读结论**（原规范路径）
- **c) 无 frontmatter（2026-09-02 前）** → 原豁免（不参与精确匹配）

> 注: 说"存量"时须限定具体含义（c 态历史豁免 / 过渡期 b 态）——不泛指。

**规划载体定位（A 阶段：会话隔离——读取切片 + 写断言）**:
1. **读取切片**: 读取 `.qoder/plans/plans.json` 时**只提取当前 plan 的行**（按 id 过滤），禁止将全量 JSON 粘贴入分析上下文（多 plan 并发时无关 plan 的内容会污染决策）；需要全景（architect 规划/看板/recovery 列表）才读全量并显式声明目的
2. **定位来源**: ①会话显式指定（用户/--resume {planId}）→ ②in-progress 集合推断（唯一 in-progress 直接命中；多个时按 updated 最新并列出供用户确认）→ ③plans.json activePlan（状态合法时兜底）
3. 从 `plans[]` 中取该 plan 的 `file` 字段，读取对应详情文件 `.qoder/plans/{file}`
4. **校验 plan 状态**: 定位的 plan 必须为 `active`/`in-progress`；若为 `revised` → 提示先回 architect 修订并重新沙盘；若为 `blocked` → 检查详情记录的原因并解阻；执行中发现依赖未满足或外部阻塞 → **显式置 `blocked` 并在 plan 详情记录原因**（to_blocked 所有者见 x-rules.stateMachine.owners）
5. 校验 `qualityScore` ≥ 19（质量门禁，未达标禁止执行；简化路径豁免见下方）
6. 子 plan 还需校验父 plan 依赖是否满足（父 plan 的 children 中依赖项状态）
7. **写前断言（防并发写错对象）**: 任何状态写（status/updated）前，确认"本次登记的操作对象 == 启动时定位的 plan id"，且 plans.json 该行 `updated` 与启动时读取一致；不一致 → 挂起重读（可能被其他会话写入）
8. 若 `plans.json` 不存在 → 询问用户

**解析签名** (YAML frontmatter):
```yaml
---
signatures:
  sandbox_agent: "agentId" | "self"
  audit_agent: "agentId" | "self"
  timestamp: "ISO8601"
---
```

**验证规则**:

| 签名值 | 规划载体来源 | 结果 |
|-------|----------------|------|
| 有效 agentId | 任意 | 🟢 通过 |
| "self" | 当前会话 | 🔴 拒绝，需重新审计 |
| "self" | 其他会话 | 🟢 通过 |
| 文件不存在 | - | 🟡 警告，继续执行（需在输出中注明"沙盘报告缺失 [无独立审计凭证]"；最终审计写入 done 前需用户显式豁免） |
| 签名字段缺失（存量报告） | - | 🟡 降级：文件含通过/不通过结论即通过（2026-09-02 前存量豁免） |
| 签名字段缺失（新规范报告） | - | 🔴 拒绝，补充签名 |

- [ ] plan 详情文件已读取（核心诉求/决策/交付清单）
- [ ] 质量门禁检查: qualityScore ≥ 19（<19 挂起，不得执行；简化路径/无 plan 豁免，见下方简化路径表）
- [ ] 目标子系统规则已加载（所涉端的路径规则 `.qoder/rules/1x-{端}.md`）

**简化路径判定**:

| 场景 | 判定条件 | 简化内容 |
|-----|---------|---------|
| typo 修复 | 修改 ≤ 3 行 | 跳过关联文件、调用链、质量门禁 |
| 配置修改 | 单文件单值 | 跳过调用链、质量门禁 |
| 紧急 Hotfix | `--urgent` 参数 | 仅保留签名验证（不豁免），跳过质量门禁 |
| 其他 | - | 标准流程（含质量门禁） |

> 质量门禁统一表达式（与 01 §2 对齐）：`(存在对应 plan 且非简化路径) → qualityScore ≥ 19 强制；typo ≤3 行 / 配置单值 / --urgent / 用户显式豁免 → 跳过`。无 plan 的小修复事后按需补 plan。阈值权威见 plans.schema.json x-rules

**Red Flags 反合理化表（V2.8.1——简化路径旁对照）**

| 借口 | 现实 |
|------|------|
| "紧急 hotfix 免检查" | --urgent 仅豁免质量门禁/挂起（挂起豁免见 architect 紧急模式条款 + 本 skill「自治授权语」条款）——签名验证、构建验证、诚实约束不豁免 |

**阶段定义**: 见 `.claude/config/god-stages.yaml`

### 阶段 1: 签名验证

执行沙盘/审计报告签名验证；验证通过后**将 `plans.json` 中当前 plan 的 `status` 置为 `in-progress`**（active→in-progress 所有者 = god，见 x-rules.stateMachine.owners）。

**输出**:
```

- 结构行: VERDICT={pass|fail} (P0={n} P1={n}) ｜ 过渡期报告（无结构行）→ 人工读结论
- plans.json: {plan_id} status → in-progress

继续执行？[Y/n]
```

### 阶段 2: 上下文加载

读取 plans.json → plan 详情文件、CLAUDE.md、SOP 等上下文。

**需求基线消费（S5 流水线 · 2026-09-07）**: plan 详情含「需求基线」节（复杂度 ≥2 plan 必有）时：

- [ ] 域引用锚点已加载：business-architecture.md 命中域节（按节读，不整本）
- [ ] 复用决策锚点已加载：REUSE/PARTIAL 条目的资产路径/用法/坑（asset-catalog 条目 path——按需打开源码）；NEW 缺口不重复发明（确认记录在案）
- [ ] 表清单已加载：操作表已在 architect §1.8/T1 确认——**不重复问**（S6.5: god 按基线执行）
- [ ] 意图锚点已加载（task-103 W1 · 2026-09-09）：plan 行含 `intent` 字段 → 读 `.qoder/intents/{intent}`（5 要素，重点：期望结果/排除项——scope 对照基线）；intent 缺失（复杂度 ≥2/非 todo/新且非豁免）→ 提示补建档（audit 将按 P1 回指）
- [ ] 需求包锚点（条件触发 · 2026-09-16）：需求基线/plan 引用需求包（requirement-converger 产出）时——`需求包: {路径} v{X}` 已解析；§九 配置键位禁自创（键名表为准）；附录A L2/L3 = SQL 口径基准（参考 SQL 可等价改写，等价性以口径为准）；附录B = 对接契约照做

**场景自检（task-107 W4）**: 每次变更点对照 plan 详情「场景矩阵」自检——检查点正文新增「场景自检」小节（格式: `矩阵节引用（节名+场景标识）→ 覆盖/新增/变更`；矩阵遗漏时先补矩阵再继续——01 §5 变更点自检）。

继续执行？[Y/n]

### 阶段 4: 构建验证

执行构建验证。按以下顺序确定验证路由：

**Step 1 — 探测 Hook 存在性 → 检查自动验证结果**：

先探测 `.qoder/settings.local.json` 是否存在且含 PostToolUse 配置（易失资产，禁止假设存在）：

| 探测结果 | 判定 | 动作 |
|---------|------|------|
| 存在且已配置 | ✅ Hook 可用 | 检查其输出（下表） |
| 不存在 / 未配置 | ⚠️ Hook 缺失 | **直接进入 Step 2 手动补位**，禁止假设验证已自动完成 |

Hook 可用时，检查其输出（诊断修复命令见 01 §6，唯一权威，本 Skill 不复制命令明细）：

| Hook 输出 | 判定 | 动作 |
|----------|------|------|
| 无 FAILED 标记 | ✅ 自动验证通过 | 跳到 Step 2.5 |
| `JAVA_BUILD_FAILED` | ❌ Java 构建失败 | 按 01 §6.2 诊断修复后重验 |
| `PYTHON_IMPORT_FAILED` | ❌ Python 导入失败 | 按 01 §6.2 诊断修复后重验 |
| `FRONTEND_BUILD_FAILED` | ❌ 前端构建失败 | 按 01 §6.2 诊断修复后重验 |
| 无任何 Hook 输出 | ⚠️ Hook 未触发 | 执行 Step 2 手动补位 |

**Step 2 — 手动补位（Hook 未覆盖时）**：

修改范围 → 手动验证命令的映射表**唯一权威 = 01 §6.2**（java-bff/python-ai/frontend/frontend-admin/跨端逐端），此处不复制。执行后按 Step 2.5 继续。

**Step 2.5 — 测试验证（构建通过后强制——出口三态，task-109 W6）**：

① **有测试资产**（验收标准: 套件命令可跑且有断言）→ 执行套件：

| 修改范围 | 测试命令 | 通过标准 |
|---------|---------|---------|
| `java-bff/**` | `cd java-bff && mvn test` | 全部通过，无 ERROR/FAILED |
| `python-ai/**` | `cd python-ai && uv run pytest` | 全部通过，无 ERROR/FAILED |
| `frontend/**` | `cd frontend && npm run test`（如有测试脚本） | 通过 |

② **无测试资产 + 核心逻辑变更** → 阶段 3 检出并补建最小测试（≥1 条单行为断言，垂直切片，该端既有最轻量手段——如 frontend 沿用 test:scene esbuild+node 模式）；本步执行并记录 `补建: {用例名}`。

③ **无测试资产 + 非核心**（纯样式/文案）→ 豁免记录：形态标注（缺资产/坏资产——坏资产=存在但命令不可执行）；理由写入检查点正文「测试豁免记录」小节；本步输出 `⚠️ 豁免（理由: …；形态: …）`。

> 坏资产与零资产同归"无测试资产"并区分形态；三态口径权威见 01 §6.3「测试证据出口」；豁免正当性的 audit 核对见 audit SKILL 审计重点表。
> 简化路径（01 §2 typo/配置单值/注释文档）豁免 Step 2.5/2.7/2.8。

**Step 2.7 — 场景级验证（01 §6.3，核心逻辑/接口/流程变更强制）**：

对照规划阶段 01 §4.1 多场景矩阵与边界清单逐项闭环：

| 变更类型 | 场景级验证动作 |

**Step 2.8 — 启动冒烟（L2，条件触发——01 §6.3 验证深度分级）**：

**触发条件**: 变更面含**装配/配置/依赖拼接类**（新增/重命名被框架扫描类、配置中心/环境变量/端口/依赖注入变更）**且存在可运行环境**（**装配类判定以事实为准——V2.9.1**: 被框架扫描注册的类型/资源的增删改（控制器/映射器/配置类/路由注册等——实例清单按端级规则映射）达到批量规模或改变装配结构时，**按装配类触发完整验证，不依赖 plan 的变更面标注**）；两者任一不满足 → 标记「未触发」并在检查点显式记录原因（防静默跳过——"显式失败优先"原则的自我应用）；**简化路径命中（01 §2）→ 记「简化路径豁免」不记「未触发」（豁免优先）**。目的：发现只在应用启动/装配时暴露的缺陷（符号简名装配冲突/启动配置缺陷——01 §6.3 L2 行）。

**操作（按序）**:

1. **符号唯一性扫描**（变更含新增/重命名被框架扫描类时）: 全仓提取类声明简名聚合计数，重复简名 = 装配冲突预警。双形态示例（路径按端调整）:

```
PowerShell: Get-ChildItem -Recurse -Filter *.java src\main | Select-String -Pattern 'class\s+([A-Za-z0-9_]+)' | ForEach-Object { $_.Matches[0].Groups[1].Value } | Group-Object | Where-Object Count -gt 1
grep:       grep -rhoE 'class[[:space:]]+[A-Za-z0-9_]+' src/main/java --include='*.java' | awk '{print $2}' | sort | uniq -d
```

2. **依赖通道全探**: 依赖系统（配置中心/注册中心/DB 等）的**所有协议通道**逐一探测——不只 HTTP（配置中心类系统常有独立端口通道）；缺通道 → 先修通道再启动。
3. **端口占用者身份核验**: 目标端口被占时先核占用者身份（进程/归属判定）——同族系统在跑 → 换端口适配，禁止误杀在跑系统。
4. **启动 + 关键链路探活**: 按端级规则启动应用 → 启动日志无致命错误 + ≥1 条关键链路探活；**探活有效性判据（V2.9.1）**: 探活目标必须与**本次变更的功能面相交**——框架级/无功能语义的端点（健康检查、框架会话等）**不构成功能面验证证据**；无功能面探活 = 冒烟未完成，不得记「通过」。
5. **形态对齐检查（V2.9.1）**: 验证前以系统自述信号（启动输出/健康端点/版本端点）确认**被测实例运行形态与验证目标形态一致**（如：依赖已启用形态 vs 降级/受限形态）；不一致的验证视为无效；验证记录须标注被测形态。**降级形态行为核验**: 依赖或能力未启用形态下，系统行为必须匹配契约声明的失败策略（显式告警/降级响应/阻断启动）；静默降级判缺陷（无契约声明时登记为缺陷候选）。
6. **冒烟实例回收（V2.9.1）**: 冒烟完成后临时/独立实例必须回收闭环（进程终止 + 端口释放核验）；无法回收时登记「实例台账」（进程/端口/用途/状态）并在交接中显式移交——禁止遗留无名实例污染后续验证现场。

**证据与落点**: 启动日志摘要 + 探活结果 + **被测形态与未验证面声明**写入**检查点正文「启动冒烟记录」小节**（格式: `| 检查项 | 结果 | 证据 |` + `被测形态: …` + `未验证面: …（原因/挂起登记）`；未触发态记录原因）；受限环境无法覆盖的验证面必须显式声明并登记挂起，**禁止以低层级证据（可编译/可启动/框架端点通过）顶替功能面验证目标**；交付回填并入 plan 详情「验证证据」节。
**失败出口**: 阻断——修复后重跑（与 Step 2.5 出口风格对齐），启动冒烟失败禁止进入阶段 5。

## 🔄 TDD 迭代协议（PLAN-红-绿-重构循环）

**适用**: 执行策略表映射为 TDD 迭代的任务（新功能 + 有测试 / Bug 修复 + 有测试）。
**测试套件检测**: 见上方"测试套件检测"（Java/Python/TypeScript 规则唯一处）。
**方法论细则**: 上下文感知/测试规划/行为中心/垂直切片/重构指南全文见 [references/tdd-iteration.md](./references/tdd-iteration.md)（渐进式引用，本节仅骨架 + 护栏）。

### 循环本体（每轮 5 步）

```
0. PLAN: 测试规划（确认行为 → 确认公开 API 入口 → 可测试性设计）；输入 = plan 场景矩阵 01 §4.1；
        上下文感知：测试名/接口词汇对齐领域语言（business-architecture.md / 契约），尊重既有 ADR
1. RED: 写一个失败测试（单行为单测试；必须使用真实消息结构/真实数据形状——伪造结构会掩盖字段路径缺陷；
        行为中心：通过公开 API 断言行为，不测私有实现细节）
2. 确认失败: 运行该测试，确认失败原因是"实现缺失"（而非测试自身错误）
3. GREEN: 最小实现使测试通过（禁止过度实现/猜测性代码）；垂直切片：一轮一行为
4. REFACTOR: 仅全绿后执行；复制提取→模块加深→SOLID；测试须零修改（重构需改测试=耦合实现细节）；可跳过须注明
```

> 垂直切片 vs 水平切片: 禁止先写全部测试再写全部实现（水平切片 → 中间态无法验证、失败定位模糊、套件脆弱）；一轮 = 一个行为闭环后进入下一轮。

### 迭代状态记录（每轮循环写入检查点）

```
TDD 检查点: .qoder/skills/audit/checkpoints/checkpoint-{planId}-{ts}.md (type=tdd)
- 本轮测试名 / 失败原因 / 实现变更 / 测试结果
```

### 与验证体系衔接

- 边界用例（空值/极限/并发/权限）按 01 §4.1 场景矩阵在 GREEN 后补充，逐项闭环
- 全部轮次结束后进入阶段 4（构建 + 测试 + 场景三路由验证）
- **失败计数**: 同一测试失败 ≥2 次（**从 GREEN 修复尝试起算，RED 阶段的"确认失败"不计入**）或 总迭代 ≥5 轮 → 熔断（见下方 TDD 熔断机制）

### 协议约束

- 🚨 禁止跳过 RED 直接写实现（跳过 = 声明切换 Standard 协议，须在输出中标注理由）
- 🚨 测试必须触达被测对象本体（只测依赖库 = 绕过代理层缺陷，无效证据）
- 🚨 测试必须使用真实消息结构（伪造结构会掩盖字段路径缺陷）
- 🚨 测试名/接口词汇与领域语言对齐，违反既有 ADR 须挂起说明（见 references/tdd-iteration.md §一）

### 执行账本与裁决记录（V2.8.0）

**执行账本（行式追加——防压缩/支撑 recovery 与 --resume 机械扫描）**: 检查点正文「执行账本」节，每关键事件追加一行 `- {ISO 时间} {事件类型}: {明细}`；事件类型: `task-complete / fix-round / ruling / parked / blocked / decision`（`ruling`=含若错代价的裁决三要素齐；`decision`=流程性决策）；**追加式**（禁止修改历史行）；扫描容忍 `- ` 前缀（正则 `^-?\s*{ISO}`）。写入时机: 任务拆解项完成 / 修复轮（**镜像 plan 详情节——触发方（sandbox/audit 主 Agent）执行：检查点存在时追加账本 fix-round 行，缺席时以 plan 详情「修复轮次记录」节为唯一载体**）/ 自主裁决 / 熔断。**格式豁免口与判别示例（task-126 Meta 落地）**: 纯进度行可省略类型段（保持行首 ISO 时间锚——扫描正则兼容）；**治理性事件行（fix-round/ruling/blocked/parked/decision）必须含类型段**。判别: "阶段 3 完成"=进度行（可省）；"修复轮次 R2 触发"=fix-round；"采纳 CR-101 方案 b"=decision；"驳回延期修复（若错代价: 累积风险）"=ruling（三要素齐）。
**写入时机矩阵（task-126-1 设计要点 7 升格——固定锚）**:

| 事件 | 写入者 | 载体 |
|------|--------|------|
| 打回（P0>0） | sandbox/audit 主 Agent | plan 详情 R{n} 行 + 检查点账本 fix-round 行 |
| 复验回迁 | sandbox | plan 详情处置行 |
| 超限（escalation） | sandbox/audit | plan 详情超限行 + 裁决清单（Ruling）+ 置 blocked |
| 人工裁决 | god/recovery | plan 详情 ruling 行 |
| god 自主裁决 / CR 仲裁 | god / 编排主 Agent | 检查点账本 ruling 行（镜像至 plan 详情「裁决记录」） |

冲突口径: 执行期以账本为暂态依据、同步完成后以 plan 详情「裁决记录」为准，不一致触发补同步。
**裁决记录（Ruling 落账）**: `Ruling: <决策> — <理由> — <若错代价>` + 来源标注（god 执行/CR 仲裁/P1 裁量/超限裁决）；表格落检查点「裁决记录」节（模板见 checkpoint.md）。执行中一切自主取舍必须落账——**"随工作区消亡的裁决=秘密决策"**。**镜像与补同步（阶段 5 收口时执行）**: god 自主裁决/CR 仲裁 → 检查点账本 ruling 行；收口时镜像入 **plan 详情「裁决记录」节**（载体定义: plan 详情新增节，列与检查点表同构——决策/理由/若错代价/来源/时间）——执行期以账本为暂态依据、同步完成后以 plan 详情节为准，不一致触发补同步。完成汇报时穷尽列出本 plan Ruling 清单（引用检查点账本）。

**自治授权语（V2.9.0——外部体系吸收）**

用户显式授权本任务自治执行（如"全程自主，仅异常挂起"）时——除 4 类停止条件外**不逐阶段询问**（阶段确认改为全量落账：授权语 + 全部 Ruling → 检查点账本 ruling 行，完成汇报穷尽列出）。**防伪**: 无落账记录 = 视为未授权（对齐确认卡防伪 V-A8 先例——授权凭证 = 账本 ruling 行 / plan 详情「裁决记录」节）。

**4 类停止条件（可判定定义）**: ① **不可逆操作**=删除/覆盖不可恢复数据、推送远端、对外发送消息等无撤销手段的动作；② **安全敏感**=凭证/密钥处理、权限边界变更、安全开关改动（对齐 parallel-orchestration 合批判据口径）；③ **工作区外副作用**=修改工作区之外的文件/系统状态、调用外部服务产生持久影响；④ **计划性崩溃**=会话/平台级中断预兆（上下文耗尽、平台终止）或执行框架级失败——立即停（不做自动恢复尝试）。

**保留句**: 既有阻断/熔断/不确定挂起（01 §1）机制不受授权影响；**`/clear` 强制挂起不豁免**（跨端防污染机制非阶段确认）。**落账精度**: 授权语落账事件类型=decision；检查点未创建时（授权先于阶段 1）载体=plan 详情「裁决记录」节。**模板层保留（声明不改）**: 写入规则表"询问用户"列与 6 处 [Y/n] 模板（5 阶段输出块 + 检查点模板块）——授权模式下按本条款解释"落账代替询问"。
