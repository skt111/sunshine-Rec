# 执行公约 (Execution Protocol)

> 来源: `.claude/CLAUDE.md` §0.5 | 始终生效（无加载 frontmatter）

除非被显式覆盖，以下规则适用于所有任务。

## 1. 不确定即挂起

| 场景 | 行为 |
|-----|------|
| 意图模糊 / 需求悖论 | 立即挂起，澄清需求 |
| 位置不确定 | 立即挂起，精准定位 |
| 设计不理解 | 立即挂起，提问澄清 |
| 存在歧义 | 列出多种理解路径，请求选择 |

**禁止猜测式推进。**

## 2. 强制上下文检查 (修改操作前)

仅在执行**修改操作**前触发（只读操作不触发）。自检以下三项：

| 检查项 | 通过条件 | 失败动作 | 适用场景 |
|-------|---------|---------|---------|
| Plan 定位 | 已按定位来源确认当前 plan（①会话显式 → ②in-progress 集合推断/用户选择 → ③activePlan 兑底）并读取该 plan 详情 | 挂起，请用户指定 plan 或从 in-progress 列表选择 | 所有修改 |
| 读取切片 | 只读当前 plan 的行 + 详情（**禁止全量 plans.json 入上下文**——多会话并发的无关 plan 内容会污染决策） | 挂起重读 | 所有修改 |
| 质量门禁 | plan 的 qualityScore ≥ 19（统一表达式：存在 plan 且非简化路径时强制；typo ≤3 行/配置单值/--urgent/用户显式豁免 → 跳过） | 挂起，回 architect 补分 | 非简化路径修改 |
| 目标文件已读 | 已读取要修改的文件 | 挂起，读取文件 | 所有修改 |
| 上下文完整 | 理解调用链和依赖 | 挂起，补充上下文 | 非简单修改 |

**简化路径**（可跳过"上下文完整"检查）：
- typo 修复（≤3 行变更）
- 配置值修改（单文件单值）
- 注释/文档修改

🚨 **跳过检查直接修改 = 视为失败并挂起。**

## 3. 修改前必读

修改代码前，必须严格按顺序：
1. **读取目标文件**：禁止凭记忆编辑。
2. **通读关联上下文**：导出接口、直接调用方、公共工具函数。
3. **精准定位**：明确标记要修改的函数/类/行号。
4. **理解设计意图**：不理解时先提问。

**修改前取证（两条纪律——2026-09-15 长任务实验复盘吸收）**:
- **先探后修**: 修复运行/数据类缺陷前，先用**只读探针**取证（数据分布/进程端口归属/配置来源等现状事实），禁止盲改；探针只读、产物放构建目录（gitignore 区）、不入库（编码注意事项见端级规则）。
- **引用面盘点**: 修改共享术语/编号/枚举/步骤号等"被多处引用的字样"前，先全目录 grep 目标字样盘点全部引用点——一次改齐，或显式声明保留点（如版本表历史行）；禁止只改主体留引用残留（防产出后自相矛盾）。

## 4. 设计验证检查点 (实现前)

在开始实现前，自问：
- [ ] **是否存在更简单的方案？**（第一性原理检验）
- [ ] **当前设计是否超出需求边界？**（过度设计检测）
- [ ] **是否引入了不必要的抽象层？**（复杂度控制）

🚨 若任一项回答"是"或"不确定"，立即挂起并请求澄清。

### 4.1 多场景矩阵与边界条件清单（规划阶段强制产物）

完成设计验证后，**规划阶段必须输出**，随任务规划载体落盘（内嵌章节，不新建独立文件）：

1. **多场景矩阵**: 覆盖正常 / 异常 / 极限 / 空值 / 并发 / 权限 / 超时 7 类场景，逐场景描述预期行为。
2. **边界条件清单**: 边界值、临界状态、依赖缺失、竞态条件等边界情况。
3. **反向用例**: 至少 1 个"按错误理解需求会怎么实现"的反向用例，验证方案抗误读。

**落盘模板（task-107 W4 · 2026-09-10——plan 详情三节标准格式）**:

① 「场景矩阵」节:

```markdown
| 类别 | 场景 | 预期行为 | 验证方式 |
|------|------|---------|---------|
| 正常 | …  | …       | …       |
（7 类逐类 ≥1 行；无场景类别显式写 `N/A（理由）`——S5 括号式样；"类别"列供 audit 逐类核对；"验证方式"列按 §6.3「验证工具路由」填写——推荐制，自由填写合法）
```

② 「边界清单」节（格式同表）: `| 类别 | 边界 | 预期行为 | 验证方式 |`（边界值/临界状态/依赖缺失/竞态）

③ 「反向用例」节: ≥1 个"按错误理解需求会怎么实现"用例（误读实现 → 为何拒绝）

> **轻量豁免**: complexity <2 可精简为 3 类（默认 正常/异常/空值，或由 architect 显式声明所选类）；存量 plan（created ≤ 2026-09-10）不追溯——audit 标注『矩阵缺失（存量）』不判 P1。
> **消费方**: god 阶段 3/4 对照逐项验证记录（检查点「场景自检/场景验证记录」小节）；audit 逐行核验（分级见 audit SKILL 审计重点表「多场景/边界覆盖」行）。

**规划载体落位（统一路径）**:

| 体系 | 规划载体 |
|-----|---------|
| 本项目统一（双轨共享易变资产，规划统一收口） | `.qoder/plans/plans.json`（索引）+ `.qoder/plans/{id}-{slug}.md`（详情） |

> 历史说明: 原三态落位（`.claude/plan/BUILD_PLAN.md` / `.qoder/plans/` / `.codebuddy/plan/`）已于 2026-09-02 收口为单一 `.qoder/plans/`。`.claude/plan/` 仅保留运行时资产（交接棒/雷达/归档）；`.codebuddy/plan/` 轨道维持 BUILD_PLAN 直至停用（CodeBuddy 轨道不参与本项目双轨共享）。

> 简化路径判定（§2 typo ≤3 行 / 配置单值 / 注释文档）豁免本小节。

## 5. 修改中约束

- **外科手术式**：仅改动绝对必要的部分。切勿"顺手优化"相邻代码。
- **简单至上**：仅用最少代码解决问题。杜绝"以防万一"的猜测性实现。
- **遵从规范**：规范一致性 > 个人技术偏好。若有异议，显式提出。
- **变更点场景自检**: 每次变更点对照 §4.1 多场景矩阵与边界清单自检，未覆盖场景禁止进入下一阶段；发现矩阵遗漏时先补矩阵再继续。
- **写盘核验（执行纪律）**: 写盘动作报告失败时，先读回目标文件核验是否已写入（平台存在偶发误报）——未写入再重试，禁止不核验的重复写入/误判失败（2026-09-15 复盘吸收）。

## 6. 修改后构建验证 (强制)

完成代码修改后，**必须强制执行构建验证**。

### 6.1 自动触发路由（PostToolUse Hook）

`.qoder/settings.local.json` **若存在**（易失资产，被 .gitignore 排除，存在性需运行时探测）且配置了 `PostToolUse Write|SearchReplace|edit_file` Hook，则每次文件编辑后自动执行 `.claude/scripts/smart-build.mjs`（跨平台调度器），按文件路径自动检测子系统并触发对应构建命令：

| 文件路径模式 | 自动执行命令 |
|------------|------------|
| `java-bff/**` | `mvn compile -q` |
| `python-ai/**` | `python -c "import main"` |
| `frontend/**` | `pnpm build` |
| `.qoder/plans/plans.json` | `node .qoder/plans/validate-plans.js`（编辑后自动校验，失败输出 `PLANS_VALIDATE_FAILED`） |
| `.claude/**` / `.qoder/**`（其余） | 跳过（配置文件无需构建） |

**Hook 输出约定**：成功无额外输出；失败时输出 `JAVA_BUILD_FAILED` / `PYTHON_IMPORT_FAILED` / `FRONTEND_BUILD_FAILED` / `PLANS_VALIDATE_FAILED` 标记。

🚨 **Hook 缺失降级（运行时探测）**: 探测 `.qoder/settings.local.json` 不存在或未含 PostToolUse 配置时，**禁止假设验证已自动完成**，必须按 §6.2 手动补位执行。

### 6.2 手动补位路由（Hook 未覆盖时）

以下场景 **必须手动执行** 构建验证：

| 场景 | 验证命令 |
|-----|----------|
| Hook 未触发或输出为空 | 按 6.1 表格手动执行对应命令 |
| `frontend-admin/**` 修改 | `cd frontend-admin && npm run build` |
| 跨端修改（≥2 子系统） | 逐端执行对应构建命令 |
| Hook 输出 FAILED 标记 | 诊断修复后重新执行对应构建命令 |

🚨 **禁止跳过上述步骤直接汇报"任务完成"！**
🚨 **Hook 自动触发 ≠ 可跳过验证**：确认 Hook 输出无 FAILED 标记后方可继续。

### 6.3 场景级验证（构建验证之上，强制）

构建通过 = 验证起点，非终点。

**验证深度分级（L0-L3——2026-09-15 长任务实验复盘吸收）**: 验证体系的完备性 = 与缺陷分布的匹配度——每一层只能覆盖对应存在面，缺一层 = 一层盲区。

| 级别 | 验证面 | 典型手段 | 可发现缺陷（示例） |
|------|--------|---------|------------------|
| L0 | 构建/类型 | 编译构建（§6.1/6.2） | 编译/类型错误 |
| L1 | 静态审计 | sandbox/audit 蓝军 | 逻辑断链/契约矛盾/条目遗漏（构建绿灯下） |
| L2 | 启动冒烟 | 应用可启动 + 关键链路探活（god 阶段 4 Step 2.8：前置检查 → 启动 → 探活） | 装配冲突（被扫描类简名）/启动配置缺陷 |
| L3 | 集成联调 | 真环境数据面走通（收口验证轮） | 环境适配（键位/通道/数据族属） |

**下限规则**: 变更面含装配/配置/依赖拼接类时且存在可运行环境 → 验收面不得低于 L2（简化路径除外——01 §2）；低层绿灯不得宣称"可交付"（构建绿灯 ≠ 可运行）。
**L3 执行锚点**: L3 时机 = 验收级别声明为 L3 时的收口验证轮（由 architect 输出「验收级别声明」驱动——防"有分级无人负责"）。
**形态对齐（2026-09-30 跨项目失败复盘吸收）**: 凡变更触及装配图/配置/依赖拼接面——验证前必须对齐"被测实例运行形态 vs 验证目标形态"（以系统自述信号确认）；验证记录必须标注被测形态；交付声明必须标注未验证面。**降级/受限形态行为属验收面**: 依赖或能力未启用形态下，系统行为必须匹配契约声明的失败策略（显式告警/降级响应/阻断启动）——静默降级判缺陷。

> 与"场景级验证"关系: 本分级规定"验到多深"（深度维），下方场景表规定"验什么场景"（内容维）——两者正交叠加。

以下变更**必须**叠加场景级验证：

| 变更类型 | 场景级验证要求 |
|---------|--------------|
| 核心逻辑/分支变更 | 单测补充边界用例（空值/零值/极限/并发），对应 §4.1 场景矩阵逐项闭环 |
| 接口/契约变更 | 接口多场景验证（正常/异常/权限/超时/参数非法），跨端逐端执行 |
| 状态机/流程变更 | 状态流转边界推演（如沙盘 32 场景式时序推演），至少覆盖异常回退路径 |

**验证工具路由（task-109 W6——推荐制: 默认走推荐；自由填写合法）**:

| 场景类别 | 首选验证工具 | 备选 |
|---------|------------|------|
| 核心逻辑/分支 | 单元测试（边界用例） | 推演矩阵 |
| 接口/契约 | 契约场景验证（curl/pytest） | 集成测试 |
| 状态机/流程 | 状态流转推演矩阵 | 单测（可叠加） |
| 跨端用户旅程 | E2E/浏览器验证（优先查 `.claude/context/e2e-golden-paths.md` 黄金路径登记——存在则按登记方式验证；缺失不阻断） | 手动验证记录（截图+断言清单） |
| 纯样式/布局 | 截图对比 | 人工目检 |
| 数据/迁移 | dry-run + 数据核对 | - |

**测试证据出口（task-109 W6——三态；无测试资产不可无声跳过）**: 修改范围含核心逻辑时，测试证据必居其一：

| 态 | 条件 | 动作 | 记录式样 |
|----|------|------|---------|
| ① | 有测试资产（验收标准: 套件命令可跑且有断言） | 执行套件 | `✅ X passed` |
| ② | 无测试资产 + 核心逻辑变更 | 阶段 3 检出并补建最小测试（≥1 条单行为断言，垂直切片，该端既有最轻量手段） | `补建: {用例名}` |
| ③ | 无测试资产 + 非核心（纯样式/文案） | 豁免记录（形态标注: 缺资产/坏资产；理由写入检查点「测试豁免记录」小节） | `⚠️ 豁免（理由: …）` |

> 坏资产（存在但命令不可执行）与零资产同归"无测试资产"并区分形态；简化路径（§2）直通不触发三态；豁免正当性由 audit「测试证据审计」行核对（保真）。

**证据要求**: 场景验证结果随交付记录（单测用例名 / 场景推演矩阵 / 端到端验证记录），禁止口头宣称"覆盖"。

**验证证据链（三段强引用，2026-09-11——better-harness finding 修复）**: 场景验证结果随交付记录流转的完整链：

| 段 | 落点 | 内容与责任 |
|----|------|-----------|
| ① 逐行证据 | 检查点正文「场景验证记录 / 测试豁免记录 / 场景自检」小节（落点见本 §6.3 上文各步） | 矩阵行级结果与证据（god 阶段 4 记录） |
| ② 交付结论 | plan 详情「验证证据」节（阶段 4 全部验证完成后回填） | 三态结论 + 关键结果 + 检查点文件引用（引用式）；god 阶段 4 收口 |
| ③ 核对记录 | audit 报告「测试证据审计」节 | 逐条追溯到 ①②、引用证据位置；链路缺失/不一致判 P1（audit 终审） |

> 存量 plan（created ≤ 2026-09-10，与 §4.1 矩阵 carve-out 同口径）不追溯——audit 标注『验证证据节缺失（存量）』不判 P1。

🚨 **构建验证通过但场景验证缺失 = 不得汇报"任务完成"。**
> 简化路径判定（§2）豁免本小节。

## 7. 诚实约束

- **显式失败**：若有步骤被跳过，宣称"已完成"即为错误。
- **暴露冲突**：若两种模式矛盾，明确择一并阐明理由。
- **极简输出**：只提供影响决策的关键信息，剔除寒暄与废话。
