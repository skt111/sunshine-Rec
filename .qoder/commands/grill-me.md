# Grill Me 命令 - 需求追问模式 V2.1（Qoder 权威版）

对任务计划或设计进行**设计树式**结构化追问，直到达成共识（无静默假设），确保信息完整后再执行。
本文件为 **Qoder 侧唯一权威**（2026-09-04 整合：吸收 .claude V2.0 决策树版 + mattpocock/grilling 最新轮次模型，Claude 侧停止独立维护）。
> V2.1 修订（2026-09-16）: 联动需求收束器（requirement-converger）——新增 §3.6 需求覆盖体检与双机路由；轮次格式增【必答/可默认】标记；终止规则增"非阻塞登记"；§5 共识摘要并轨留白登记表。

## 触发时机

以下场景必须启动本命令：

| 场景 | 触发条件 |
|-----|---------|
| 架构设计 | 架构决策前 |
| 新功能实现 | 需求边界需确认 |
| 跨端修改 | 涉及 ≥2 子系统 |
| 业务逻辑变更 | 核心业务流程 |
| 复杂修改 | 修改 ≥3 个文件 |
| 调研裁决 | 资产复用/域归属/表相关等价值判断（S6 确认协议场景） |

## 核心原则（CRITICAL）

```
🚨 事实优先探索 ──── 能从代码库/环境找到的事实，绝不问用户
🚨 事实 AI 自取 ──── 环境可查的事实（文件/工具/DB）派 sub-agent 查，探索中不阻塞其余问题（仅下游等待）
🚨 决策归属用户 ──── 只问决策，不问事实；每个决策给出推荐答案
🚨 无静默假设 ──── 设计树所有分支访问完（frontier 空）才算完成，禁止带着未问假设进入执行
```

## 执行流程（设计树 × 轮次推进）

### 1. 理解主题与构建设计树

识别主题类型（技术方案/架构设计/实现计划）→ 构建**设计树**：每个决策分支展开依赖它的子决策。

### 2. 轮次推进（frontier 模型）

**frontier** = 前置决策已定的可问决策集。每轮：

```
1. 计算 frontier（依赖已解决 → 现在可问；依赖本轮回其他问题 → 属下一轮）
2. 一轮问整个 frontier：每个问题编号 + 给推荐答案
3. 等待用户回答 → 回答重塑设计树 → 重算 frontier → 下一轮
4. 终止：frontier 空 = 所有分支访问完、无静默假设 → 输出共识，用户确认后才行动
```

> **非阻塞登记（2026-09-16）**: 用户异步/不回复的题 → 按推荐默认推进并**显式登记**"留白（待确认）"（见 §5 共识摘要）——登记后的默认 = 显式决策，不算静默假设；**未登记**的假设仍属禁止项。登记条格式：`Q{n}｜默认=<值>｜出处=<推荐/材料>`；用户后续明确答复时以答复为准并更新留白表（撤回默认）；等待期：同一 frontier 至少一轮交互间隔。

**轮次格式**：

```markdown
## 🔎 追问轮次 N（设计树位置: <当前路径>）

### 探索发现（事实自取结果）
[从代码库/环境查得的事实，标注来源]

❓ **Q1** - **<决策标题>**: <决策正文，含多个选项>
➡️ <推荐答案 + 理由>

❓ **Q2** - **<决策标题>**: <决策正文，含多个选项>
➡️ <推荐答案 + 理由>

---
请逐项回复（如 "Q1=A, Q2=B"），或提供您的答案。
```

> 问题标记: 每题标【必答】（阻塞推进）或【可默认→<默认值>】（用户不答按默认推进并登记留白——见上方非阻塞登记），标记置于 Q 编号后。

### 3. 探索优先与问题分类

**在提问前先探索**：查找现有实现/接口/调用链/约束（结合 S5 资产调研与域档案）。
分类处理：

| 问题类型 | 示例 | 处理方式 |
|---------|------|---------|
| 事实问题 | 有哪些 API？表结构？现有 util？ | AI 探索（grep/读码/DB 查询/sub-agent），**不问用户**；未决探索只阻塞下游问题 |
| 决策问题 | 新增 or 复用？JWT or Session？ | 问用户，提供推荐（决策树节点） |

### 3.5 调研确认衔接（S6 确认协议）

当追问涉及**调研裁决**（复用对象/域归属/表相关/风格选择）时，决策点输出为**确认卡**格式（发现/推断/影响面/选项/推荐），分级与防伪规则见 Spec S6——本命令为确认卡的执行载体之一。

### 3.6 需求覆盖体检与双机路由（联动 requirement-converger · 2026-09-16）

**覆盖体检（条件触发）**: 追问主题为"新功能实现 / 大需求 / 长任务"时，先按需求收束九类清单做**标题级覆盖自检**——目标与角色 / 功能与页面 / 域划分 / 技术栈与端 / 数据（关联·口径·物理属性）/ 外部依赖 / 运行环境 / 约束与负面清单 / 验收标准。设计树只覆盖决策面；本体检补数据 / 环境 / 验收面盲区（task-100 实证：缺陷多发于此三面）——缺面问题纳入本轮 frontier。

**双向路由**:
- 需求广度缺口（页面 / 数据 / 环境等需清单化的整包收束）→ 建议先走 requirement-converger（SOP §0 前置层）产出需求包，再回来做设计树追问；
- 架构决策类问题（技术选型 / 边界裁决）→ 由本命令裁决（requirement-converger 不做架构设计——其留白"可自行设计"项在此收敛）。

### 4. 探索配合（协议唯一权威 = architect §1.8）

当追问涉及数据模型、表结构、字段语义时：

- **数据源确认 / 表清单核对 / DDL 建模闭环**的执行协议见 **architect skill §1.8**（唯一权威定义，本命令不重复定义），按需调用其中 Step A-C
- 本命令的职责边界：**决策点追问**（业务规则、边界条件、选项裁决）；**事实查证**（表结构/字段语义/数据分布）交由 Oracle MCP 查询完成
- 产出统一落盘 `.qoder/plans/explorations/{topic}-{date}.md`，供 plan 引用

> 分工：grill-me 负责"问决策（树形轮次）"，MCP/扫描负责"查事实"，architect §1.8 负责"定协议"——三者各司其职，避免协议双定义。

### 5. 达成共识后执行

澄清完成后，输出**共识摘要**（全部决策 + 理由 + **留白登记表**：未答 / 待确认项按三分法【可自行设计 / 必须对齐 / 待确认】列示——与 requirement-converger 留白登记并轨，登记 ≠ 静默假设），衔接 plan「需求基线」节（S5 规范：域引用/复用决策/风格声明/表清单/确认记录）→ 按 `.qoder/rules/01-execution-protocol.md` 执行公约推进任务。

## 禁止跳过澄清的场景

- ❌ 跨端新功能开发（必须明确 API 契约）
- ❌ 业务流程变更（必须确认边界条件）
- ❌ 数据库结构修改（必须确认影响范围）
- ❌ 安全相关修改（必须确认安全等级）

**违反此规则 = 任务强制挂起**
